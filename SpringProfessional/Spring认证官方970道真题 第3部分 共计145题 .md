## Question #1

### Question


Question: In Spring MVC, is the following statement correct?

`@Controller` and `@RestController` can be used interchangeably.

**(A)** True

**(B)** False
### Explanation


In Spring MVC, `@Controller` and `@RestController` are two distinct annotations with different purposes:

* `@Controller`:  
  Used to define a web controller that typically returns a view, such as a Thymeleaf or JSP template. It is used in traditional MVC applications where the controller handles the request, processes the data, and returns a view name to be resolved by a view resolver.
* `@RestController`:  
  A convenience annotation that combines `@Controller` and `@ResponseBody`. It is used in RESTful APIs to return data directly in the HTTP response body (e.g., JSON or XML). It bypasses the view resolution process.

These annotations cannot be used interchangeably because they are designed for different response types. Using them incorrectly can lead to unexpected behavior in your application.

The `@PostConstruct` and `@PreDestroy` annotations are part of the JSR-250 specification and are used in the Spring Framework to define lifecycle callback methods for beans. These annotations allow developers to specify methods that should be executed during the initialization and destruction phases of a bean's lifecycle.

1. `@PostConstruct`:

   * Called after the bean's properties are set (dependency injection is complete) but before the bean is fully initialized.

2. `@PreDestroy`:

   * Called before the bean is destroyed, allowing for cleanup operations.
   * Executed before the `destroy()` method of the `DisposableBean` interface.
3. `CommonAnnotationBeanPostProcessor`:

   * This post-processor is responsible for recognizing and processing the `@PostConstruct` and `@PreDestroy` annotations.
   * It is automatically registered in most Spring configurations but can also be explicitly added if needed.

### Explanation


In Spring Framework, component scanning is a mechanism that allows Spring to automatically detect and register beans in the application context. Question: How can you auto-inject a Spring bean into a field by specifying its name?

**(A)** With the name attribute of the @Autowired annotation

**(B)** By using the single @Qualifier annotation

**(C)** By using both the @Autowired and the @Qualifier Spring annotations

**(D)** By using the @Autowired annotation and naming the field with the bean name
### Explanation


In Spring Framework, the `@Autowired` annotation is used to enable dependency injection. By default, Spring uses **type-based autowiring**, meaning it tries to match a bean by its type. If multiple beans of the same type exist, you can use the `@Qualifier` annotation to specify which bean to inject by its name.

**Example:**
```java
@Component("beanA")
public class MyBeanA {
    // Bean implementation
}

@Component("beanB")
public class MyBeanB {
    // Bean implementation
}

@Component
public class MyService {
    @Autowired
    @Qualifier("beanA")
    private MyBeanA myBean; // Injects the bean named "beanA"
}
```

In this example:

* `@Autowired` enables autowiring.
* `@Qualifier("beanA")` specifies which bean to inject by its name.

**Common Misconceptions:**

1. **Field Name Matching**:  
   The name of the field does not influence autowiring. You must use `@Qualifier` to explicitly specify the bean name.
2. `@Autowired` **with** `name` **Attribute**:  
   The `@Autowired` annotation does not have a `name` attribute. Bean name specification must be done using `@Qualifier`.

### Explanation


Transaction isolation levels define the degree to which the operations in one transaction are isolated from those in other transactions. The isolation level determines the visibility of intermediate changes made by one transaction to other concurrent transactions. Dirty reads occur when a transaction reads data that has been modified but not yet committed by another transaction.

**Isolation Levels in Spring:**

1. **Read uncommitted**:

   * Allows dirty reads, meaning a transaction can read uncommitted changes made by another transaction.
   * Example issue: Transaction A reads data modified by Transaction B, but Transaction B rolls back, leaving Transaction A with invalid data.
2. **Read committed**:

   * Prevents dirty reads by ensuring that only committed changes are visible to other transactions.
   * Default isolation level in many databases, including PostgreSQL and SQL Server.
3. **Repeatable Reads**:

   * Prevents dirty reads and non-repeatable reads by ensuring that data read once in a transaction cannot be modified by other transactions until the transaction completes.
4. **Serializable**:

   * Provides the highest level of isolation by ensuring complete isolation between transactions.
   * Prevents dirty reads, non-repeatable reads, and phantom reads, but at the cost of reduced concurrency.

**Practical Example in Spring:** You can set the transaction isolation level in Spring using the `@Transactional` annotation:

```
@Transactional(isolation = Isolation.READ_UNCOMMITTED)
public void performTransaction() {
    // Business logic here
}
```

In this example, the `READ_UNCOMMITTED` isolation level allows dirty reads, which can lead to inconsistencies in certain scenarios.

Question: Which of the following is the most restrictive isolation level in database systems?

**(A)** READ_UNCOMMITED

**(B)** REPEATABLE_READ

**(C)** SERIALIZABLE

**(D)** READ_COMMITED
### Explanation


In database systems, **isolation levels** define how transactions interact with each other and control the visibility of changes made by one transaction to other transactions. The isolation levels are part of the **ACID** (Atomicity, Consistency, Isolation, Durability) properties of transactions.

**Key Isolation Levels:**

1. **READ\_UNCOMMITTED:**

   * **Description:** The least restrictive isolation level. Transactions can read uncommitted changes made by other transactions (dirty reads).
   * **Issues:** Allows dirty reads, non-repeatable reads, and phantom reads.
   * **Use Case:** Rarely used due to its lack of consistency guarantees.
2. **READ\_COMMITTED:**

   * **Description:** Ensures that transactions can only read committed changes. Dirty reads are not allowed.
   * **Issues:** Allows non-repeatable reads and phantom reads.
   * **Use Case:** Commonly used in many database systems for a balance between consistency and performance.
3. **REPEATABLE\_READ:**

   * **Description:** Prevents non-repeatable reads by ensuring that data read by a transaction cannot be modified by other transactions until the first transaction completes.
   * **Issues:** Allows phantom reads.
   * **Use Case:** Suitable for scenarios where non-repeatable reads are unacceptable.
4. **SERIALIZABLE:**

   * **Description:** The most restrictive isolation level. Transactions are executed in a manner equivalent to serial execution, preventing dirty reads, non-repeatable reads, and phantom reads.
   * **Issues:** Can lead to reduced concurrency and performance due to strict locking.
   * **Use Case:** Used in scenarios requiring the highest level of data consistency, such as financial transactions.

**Comparison of Isolation Levels:**

```
Isolation Level     Dirty Reads     Non-Repeatable Reads    Phantom Reads
READ_UNCOMMITTED    Allowed         Allowed                 Allowed
READ_COMMITTED      Not Allowed     Allowed                 Allowed
REPEATABLE_READ     Not Allowed     Not Allowed             Allowed
SERIALIZABLE        Not Allowed     Not Allowed             Not Allowed
```

**Why SERIALIZABLE is the Most Restrictive:**

* The `SERIALIZABLE` isolation level ensures the highest level of consistency by serializing transaction execution.
* It effectively locks entire ranges of data, preventing other transactions from modifying or inserting data that would affect the results of the current transaction.

**Key Types of Advice in Spring AOP:**

1. `@AfterThrowing`**:**

   * Executed only when a method throws an exception.
   * Commonly used for logging or handling exceptions.
   * Example:
```java
@AfterThrowing(pointcut = "execution(* com.example.service.*.*(..))", throwing = "ex")
     public void logAfterThrowing(Exception ex) {
         System.out.println("Exception thrown: " + ex.getMessage());
     }
     ```
2. `@Around`**:**

   * Provides the most flexibility by allowing logic to be executed both before and after the advised method.
   * Can handle exceptions and decide whether to rethrow them or suppress them.
   * Example:
```java
@Around("execution(* com.example.service.*.*(..))")
     public Object logAround(ProceedingJoinPoint joinPoint) throws Throwable {
         try {
             return joinPoint.proceed();
         } catch (Exception ex) {
             System.out.println("Exception caught in @Around advice: " + ex.getMessage());
             throw ex;
         }
     }
     ```
3. `@After`**:**

   * Executed after the method completes, regardless of whether it completes successfully or throws an exception.
   * Similar to a `finally` block in Java.

```java
     }
     ```
4. `@AfterReturning`**:**

   * Executed only when a method completes successfully without throwing any exceptions.
   * Cannot handle exceptions.
   * Example:
```java

     public void logAfterReturning(Object result) {
         System.out.println("Method returned: " + result);
     }
     ```

**Why Some Advice Types Are Correct:**

* `@AfterThrowing`, `@Around`, and `@After` can all execute code when an exception is thrown, although they serve different purposes.
* `@AfterReturning` cannot handle exceptions because it only executes when the method completes successfully.

**(C)** Consistency

**(D)** Durability
### Explanation


The **ACID** properties are a set of principles that ensure reliable processing of database transactions. They stand for **Atomicity**, **Consistency**, **Isolation**, and **Durability**.

**Key ACID Properties:**

1. **Atomicity:**

   * Ensures that a transaction is treated as a single unit of work.
   * Either all operations in the transaction are completed successfully, or none of them are applied.
   * Example: If a transaction consists of two operations (debiting one account and crediting another), both must succeed or fail together.
2. **Consistency:**

   * Ensures that a transaction leaves the database in a valid state, maintaining all integrity constraints.
   * The database transitions from one valid state to another.
   * Example: If a transaction violates a foreign key constraint, it will be rolled back to maintain consistency.
3. **Isolation:**

   * Ensures that transactions are executed independently of one another, preventing interference.
   * The results of a transaction are not visible to other transactions until it is committed.
   * Example: Two transactions updating the same row should not see each other's intermediate changes.
4. **Durability:**

   * Ensures that once a transaction is committed, its changes are permanently saved in the database.
   * Even in the event of a system failure, the committed changes are not lost.
   * Example: After a transaction commits, the changes are written to disk.

```java
         System.out.println("After proceeding");
         return result;
     }
     ```

**(D)** Spring will throw an exception because nested transactions are not allowed by default.
### Explanation


In **Spring**, **transaction management** is implemented using **AOP (Aspect-Oriented Programming)**. When a method annotated with `@Transactional` is called, Spring creates a **proxy** that wraps the target object.  
This proxy is responsible for managing the **transactional context**.

Internal Method Calls and Proxy Bypass

Internal method calls **within the same class** bypass the proxy mechanism because the method is called **directly on the target object**, not through the proxy.  
As a result:

* The `@Transactional` annotation on the second method is **ignored** (it cannot create a new transaction, change propagation, etc.).
* However, the second method **still executes within the transaction** that was already started by the first method.

Example

```
@Service
public class MyService {

    @Transactional
    public void methodA() {
        // Transaction starts here
        methodB(); // Direct call, bypasses the proxy
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void methodB() {
        // The @Transactional annotation is IGNORED
        // But methodB still runs in the transaction started by methodA
        // It will NOT create a new transaction despite REQUIRES_NEW
    }
}
```

**Explanation:**

1. `methodA()` starts a transaction.
2. When `methodA()` calls `methodB()`, the call bypasses the proxy.
3. `methodB()` executes **within the existing transaction** from `methodA`.
4. The `@Transactional` annotation on `methodB` (including `REQUIRES_NEW`) is **ignored**.

How to Fix This Issue

1. Refactor the Code

Move the second method (`methodB`) to a **separate class**, ensuring that the call goes through the **proxy**.

**Example:**

```
@Service
public class MyServiceB {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void methodB() {
        // Now the @Transactional annotation is respected
        // A new transaction will be created
    }
}
```

2. Use Self-Injection

Inject the bean into itself and call through the **proxy reference**, not directly.

**Example:**

```
@Service
public class MyService {

    @Autowired
    private MyService self;

    @Transactional
    public void methodA() {
        self.methodB(); // Calls through proxy
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void methodB() {
        // Now creates a new transaction
    }
}
```

By ensuring that transactional method calls go through the **Spring proxy**, you allow the `@Transactional` annotations to be properly applied and the intended transaction propagation behavior to take effect.

**(C)** The parent entity will be deleted, but the child entities will be set to null.

**(D)** An exception will be thrown because JPA does not allow cascading delete operations.
### Explanation


In JPA, the `CascadeType.REMOVE` is used to propagate the delete operation from a parent entity to its related child entities. This means that when the parent entity is deleted, all associated child entities are also deleted from the database.

**Key Points About** `CascadeType.REMOVE`**:**

1. **Propagation of Delete Operation:**

   * When a parent entity is deleted, all child entities associated with it are also deleted.
   * This is useful for maintaining referential integrity in the database.
2. **Usage in Relationships:**

   * `CascadeType.REMOVE` is commonly used in one-to-many and many-to-one relationships to ensure that child entities are removed when the parent entity is deleted.
   * Example:
```java
@Entity
     public class Parent {
         @Id
         @GeneratedValue
         private Long id;

         @OneToMany(mappedBy = "parent", cascade = CascadeType.REMOVE)
         private List<Child> children;
     }

     @Entity
     public class Child {
         @Id
         @GeneratedValue
         private Long id;

         @ManyToOne
         private Parent parent;
     }
     ```
3. **Behavior:**

   * When the `Parent` entity is deleted, all `Child` entities associated with it are also deleted.
   * Example:
```java
Parent parent = entityManager.find(Parent.class, 1L);
     entityManager.remove(parent); // This will also delete all associated Child entities
     ```
4. **Important Considerations:**

   * Use `CascadeType.REMOVE` cautiously, as it can lead to unintended data loss if not properly managed.
   * It is recommended to use cascading operations only when the lifecycle of child entities is tightly coupled with the parent entity.
