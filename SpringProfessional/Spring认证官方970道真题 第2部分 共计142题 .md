### Explanation


Binding URI Template Variables with `@PathVariable`

In Spring MVC, `@PathVariable` is an essential annotation that allows you to extract values from the URI path and bind them directly to method parameters in your controller. This is commonly used in RESTful APIs where parts of the resource path are dynamic (such as IDs or names).

**Example Usage:**

```
@RestController
public class UserController {
    @GetMapping("/users/{id}")
    public User getUserById(@PathVariable("id") Long id) {
        // The 'id' parameter is automatically populated from the URL
        return userService.findUserById(id);
    }
}
```

Here, if you request `/users/42`, the method parameter `id` will automatically receive the value `42`.

**Best Practices:**

* Always validate or sanitize the values you get via `@PathVariable` to prevent security issues.
* Use descriptive variable names in your URI patterns to increase code readability.
* You can omit the value in `@PathVariable` if the method parameter name matches the URI template variable:

  ```
  @GetMapping("/users/{id}")
  public User getUserById(@PathVariable Long id) { ... }
  ```

**Related Annotations:**

* `@RequestParam` is used for query parameters (e.g., `/users?id=42`).
* `@RequestBody` is used to bind the request body to a method parameter, often with POST/PUT.

### Explanation


Rules for Defining `@Bean` Methods in `@Configuration` Classes

In Spring, configuration classes annotated with `@Configuration` are used to define beans using methods marked with the `@Bean` annotation. These beans are then managed by the Spring container.

**Key Rules for** `@Bean` **Methods:**

* The method must **not** be `private`. If it is, Spring cannot access it to create and manage the bean. Typically, `@Bean` methods are `public`, but they can also be package-private or protected.
* Method names are used as bean names by default. If you want to override this, you can provide a name in the annotation: `@Bean("myBeanName")`.
* Multiple `@Bean` methods can return the same type. Each will be registered as a separate bean, identified by its method (bean) name.
* The configuration class itself should be a top-level class (not a nested or inner class) and must be annotated with `@Configuration`.

**Example – Correct Configuration:**

```
@Configuration
public class PersonsConfiguration {

    @Bean
    public Person createPerson() {
        return new Person();
    }

    @Bean
    public Person createPerson2() {
        return new Person();
    }
}
```

Both beans will be available in the application context: one as `createPerson` and one as `createPerson2`.

**Common Pitfalls:**

* Marking a `@Bean` method as `private` will prevent Spring from managing it.
* Using `@Bean` at the class level is incorrect; it must be on methods.
* Confusion between `@Configuration` and other Spring annotations can lead to incorrect usage.

**Practical Tip:**  
Always keep your `@Bean` methods at least package-private. It's good practice to keep them `public` for clarity and compatibility.

Question: Which of the following concepts in Spring allows configuring settings such as 'required', 'requires new', and 'mandatory' to define transaction behavior?

**(A)** transaction manager

**(B)** transaction propagation

**(C)** isolation level

**(D)** transaction proxy
### Explanation


**Transaction Propagation in Spring**

**Transaction propagation** in Spring controls how transactional methods interact when one method calls another. This determines whether a new transaction should be started, an existing one should be joined, or if a method must always run within a transaction. These behaviors are set using the `propagation` attribute of the `@Transactional` annotation.

**Common Propagation Behaviors:**

* `REQUIRED` (default): If a transaction exists, join it; otherwise, start a new one.
* `REQUIRES_NEW`: Always start a new transaction, suspending any existing one.
* `MANDATORY`: Must run within an existing transaction; otherwise, an exception is thrown.

**Example:**

```
@Transactional(propagation = Propagation.REQUIRED)
public void doSomething() {
    // will join an existing transaction or create a new one
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void doSomethingElse() {
    // always runs in a new transaction
}
```

**Practical Tips:**

* Use `REQUIRED` for most business methods.
* Use `REQUIRES_NEW` when a method’s transaction must be independent.
* Always document your transaction boundaries clearly to avoid unexpected behavior.

**Best Practice:**  
Clearly understand how your service methods interact and choose the propagation behavior that matches your business requirements to avoid data inconsistencies and transaction issues.

Question: In the Spring Framework, what accurately describes the behavior of a bean with the 'prototype' scope?

**(A)** Beans with prototype scope are shared across multiple application contexts.

**(B)** A new instance of a prototype-scoped bean is created each time it is requested, and Spring does not reuse the previously created instance.

**(C)** Prototype-scoped beans are suitable for objects that are stateful and need to be shared among multiple components.

**(D)** The prototype scope is the default scope for all Spring beans.
### Explanation


In Spring Framework, bean scopes define how and when the beans are created, as well as their lifecycle within the container. The two most common scopes are singleton and prototype. Singleton scope (default) means only one instance of the bean is created per Spring container, and this instance is shared. In contrast, the prototype scope means a new instance of the bean is created every time it is requested from the container (via `getBean()`), making it ideal for stateful objects or cases where multiple instances with different internal states are required.

When a bean is defined with the prototype scope, Spring manages its instantiation and initialization, but it does **not** handle the full lifecycle: for example, any destruction callbacks specified with `@PreDestroy` or the `DisposableBean` interface are not called automatically. This means the client code is responsible for cleaning up any resources.

**Best practice:** Use prototype scope for beans that maintain state specific to a single use or client, such as form backing objects, and be cautious with dependency injection—injecting a prototype bean into a singleton can lead to undesired sharing of the prototype bean unless handled correctly (e.g., using method injection or `ObjectFactory`).  
**Example:**

```
@Component
@Scope("prototype")
public class Task {
    // Task-specific state here
}
```

When you request this bean multiple times, Spring will return a new `Task` instance each time.

**Overview**

In Spring’s JDBC module, the `JdbcTemplate` class simplifies database operations by handling resource management and error handling for you. When working with databases, you often need to execute Data Definition Language (DDL) operations like `CREATE TABLE`, `ALTER TABLE`, or `DROP TABLE`. These operations modify the database schema rather than interact with row data.

Recommended Method for DDL

For DDL operations in Spring, the `execute` **method** of `JdbcTemplate` is specifically designed for SQL statements that do not return any result set. This is ideal for running SQL that modifies schema, such as table creation or deletion, where you do not expect a result or need to map any output.

Example Usage

```
@Autowired
private JdbcTemplate jdbcTemplate;

// Create a table
jdbcTemplate.execute("CREATE TABLE employees (id INT PRIMARY KEY, name VARCHAR(100))");

// Drop a table
jdbcTemplate.execute("DROP TABLE IF EXISTS employees");
```

Why Not Use `update`, `query`, or `queryForList`?

* `update` is meant for modifying data (INSERT, UPDATE, DELETE), not schema.
* `query` and `queryForList` are for retrieving data (SELECT statements).
* Only `execute` provides a clean and intention-revealing way to run arbitrary SQL, especially for DDL.

Best Practice

* **Always use** `execute` **for DDL**: This avoids confusion in your codebase and makes the intention clear for future maintainers.
* **Keep schema changes in migrations**: For real applications, use migration tools like Flyway or Liquibase for managing schema changes rather than ad-hoc execution, but `execute` is useful for programmatic or dynamic DDL tasks.

### Question


Question: Which of the following transaction propagation behaviour will create a new transaction if one does not already exist?

**(A)** SUPPORTS

**(B)** MANDATORY

**(C)** REQUIRED

**(D)** NESTED
### Explanation


Transaction propagation determines how transactional methods interact with existing transactions. When a method annotated with `@Transactional` is called, Spring checks if there is an existing transaction and decides what to do based on the specified propagation behavior.

Common Propagation Types:

* **REQUIRED:** This is the default propagation type. If there’s already a transaction, the method will run within it. If there isn’t one, Spring starts a new transaction. This ensures that transactional work is always executed inside a transaction context.
* **SUPPORTS:** The method will join the current transaction if one exists. If not, it will run without a transaction. It never creates a transaction on its own.
* **MANDATORY:** The method must run within an existing transaction. If none exists, an exception (`TransactionRequiredException`) is thrown.
* **NESTED:** If a transaction exists, the method runs in a nested transaction (using a savepoint). If not, it behaves like REQUIRED and creates a new transaction. Nested transactions allow partial rollbacks to a savepoint without affecting the outer transaction.

Practical Example

```
@Transactional(propagation = Propagation.REQUIRED)
public void doWork() {
    // Will join existing transaction or start a new one
}

@Transactional(propagation = Propagation.SUPPORTS)
public void readOnlyWork() {
    // Will join existing transaction or run non-transactionally
}
```

Best Practices

* Use **REQUIRED** for most business service methods where you want to guarantee work is transactional.
* Use **SUPPORTS** for methods that can run either inside or outside a transaction (typically for read-only operations).
* Use **MANDATORY** if you want to ensure a transaction is always active (useful for internal API contracts).
* Use **NESTED** only when you specifically need savepoint-based rollback functionality, and your transaction manager supports it (e.g., DataSourceTransactionManager with JDBC).

Question: Which of the following methods is called first in the Spring bean lifecycle?

**(A)** afterPropertiesSet method in InitializingBean interface

**(B)** init-method as specified in the Spring XML Configuration

**(C)** Any method annotated with @PostConstruct

**(D)** Any method named 'init'
### Explanation


Understanding the order of initialization callbacks in the Spring bean lifecycle is essential for writing reliable and maintainable beans. After Spring creates a bean instance and injects dependencies, it provides multiple hooks for initialization logic. The order in which these callbacks are invoked is important when you need to perform setup actions.

Order of Initialization Callbacks

1. **@PostConstruct**  
   Any method annotated with `@PostConstruct` is called immediately after dependency injection is complete, making it the first initialization callback. This is the recommended way to run initialization logic, as it is clear, concise, and works regardless of how the bean is defined (XML or annotations).
2. **afterPropertiesSet() (InitializingBean interface)**  
   If the bean implements the `InitializingBean` interface, the `afterPropertiesSet()` method is called after all `@PostConstruct` methods. This is an older style but still supported.
3. **Custom init-method (XML or @Bean configuration)**  
   If an `init-method` is specified in the bean's XML configuration (or via the `@Bean(initMethod = "methodName")` annotation), this method will be called last in the initialization phase, after the previous two callbacks.

Practical Example

```
@Component
public class MyBean implements InitializingBean {

    @PostConstruct
    public void postConstructInit() {
        System.out.println("PostConstruct called");
    }

    @Override
    public void afterPropertiesSet() {
        System.out.println("afterPropertiesSet called");
    }

    public void customInit() {
        System.out.println("Custom init-method called");
    }
}
```

In XML:

```
<bean id="myBean" class="com.example.MyBean" init-method="customInit"/>
```

The output order will be:

```
PostConstruct called
afterPropertiesSet called
Custom init-method called
```

Best Practices

* Prefer `@PostConstruct` for most initialization logic as it is more modern and annotation-based.
* Avoid combining multiple initialization mechanisms unless necessary, to keep the lifecycle simple and predictable.
* Use `init-method` for legacy XML-based configuration or when you need to call a specific initialization method without changing the class.

Question: Which HTTP verb is commonly used to create a new entity in REST APIs?

**(A)** DELETE

**(B)** PUT

**(C)** GET

**(D)** POST
### Explanation


HTTP Methods for Resource Creation in REST APIs

When designing RESTful APIs with Spring, understanding the role of each HTTP method is crucial for building predictable and reliable interfaces. The most common methods are GET, POST, PUT, and DELETE, each serving a distinct purpose.

POST

The **POST** method is used to submit data to a resource, typically resulting in the creation of a new entity. When you send a POST request to an endpoint (for example, `/api/users`), the server processes the data and creates a new user entity. POST is *not* idempotent, meaning that sending the same request multiple times can result in multiple new entities being created.

**Example in Spring:**

```
@PostMapping("/users")
public User createUser(@RequestBody User user) {
    return userService.save(user);
}
```

PUT

The **PUT** method is intended for creating a new resource at a specified URI or for completely replacing an existing resource. PUT is idempotent: sending the same PUT request multiple times will always produce the same result. If the resource exists, it is replaced; if not, it is created.

**Example in Spring:**

```
@PutMapping("/users/{id}")
public User replaceUser(@PathVariable Long id, @RequestBody User user) {
    return userService.replace(id, user);
}
```

Other Verbs

* **GET** is for retrieving data only—never for creation or modification.
* **DELETE** removes resources and does not create or modify entities.

Best Practices

* Use **POST** to create new entities when the server determines the URI (e.g., auto-generated IDs).
* Use **PUT** when the client specifies the exact URI and for full resource replacement.
* Never use **GET** or **DELETE** for creation or modification of resources.

Question: Which HTTP verb is primarily used in REST to update an existing entity?

**(A)** PUT

**(B)** GET

**(C)** POST

**(D)** DELETE
### Explanation


In RESTful API design, the choice of HTTP verbs directly maps to the intended operation on resources. To update an existing entity, the **PUT** method is recommended and widely accepted as the standard.

How PUT Works

* **Updating an Entity:**  
  PUT is used to replace the entire resource at the target URI with the content provided in the request body. For example, sending a PUT request to `/api/products/5` with a product representation will fully update or replace product with ID 5.
* **Idempotency:**  
  PUT is idempotent, which means that making the same request multiple times results in the same server state.
* **Creation (optional):**  
  If the specified resource does not exist, PUT can be used to create it at the given URI, though this behavior should be consistent with your API design.

Partial Updates

* For partial updates (modifying only some fields of an entity), the **PATCH** verb is more appropriate. However, for full replacement or update, always use PUT.

Example in Spring

```
@PutMapping("/users/{id}")
public User updateUser(@PathVariable Long id, @RequestBody User user) {
    // update logic
    return userService.update(id, user);
}
```

Best Practices

* Use PUT to fully replace resources.
* Ensure the client sends a complete representation of the resource in the request body.
* Always use PATCH for partial updates, not PUT.
* Avoid using POST for updates to maintain REST semantics and clarity.

In Spring MVC, the return type of a controller method annotated with `@RequestMapping` determines how the framework processes the response. There are several options that allow for flexible handling of web requests:

Common Valid Return Types

* **String:**  
  Returning a String is the most common pattern in Spring MVC. The value is treated as the logical name of the view to be rendered (for example, a JSP page or a Thymeleaf template). If the method is annotated with `@ResponseBody` (or the controller is a `@RestController`), the returned String is sent directly as the HTTP response body.

  @RequestMapping("/hello")

  }
  ```

  When a controller method returns void, no view name is explicitly returned. Instead, Spring infers the view name from the request path. This can be useful for simple cases or when the response is handled directly within the method (e.g., via the `HttpServletResponse`).

  ```
  @RequestMapping("/voidExample")
  public void handleVoid(HttpServletResponse response) throws IOException {
      response.getWriter().write("Handled directly!");
  }
  ```

Other Common Valid Return Types

* **ModelAndView:** Allows returning both a model and a view name together.
* **Object/POJO:** With `@ResponseBody` or in a `@RestController`, you can return Java objects, which will be serialized to JSON or XML.
* **ResponseEntity<T>:** Used for full control over the response, including headers and status code.

### Explanation


Stereotype annotations in Spring are used to assign a specific role or meaning to a class within your application architecture. By using these annotations, you allow Spring to automatically detect, instantiate, and inject the appropriate beans into the application context. This helps to keep your codebase organized and maintainable.

Common Stereotype Annotations

* **@Component:**  
  The most generic stereotype annotation. It marks a class as a Spring component, making it eligible for auto-detection and dependency injection. Most other stereotype annotations are specializations of @Component.
* **@Repository:**  
  Marks a class as a Data Access Object (DAO). In addition to auto-detection, Spring applies exception translation to DAO methods, converting database-related exceptions into Spring's unified unchecked exceptions.
* **@Service:**  
  Indicates a service layer component, used for business logic. This annotation helps clearly distinguish service classes from other types of beans, improving code readability and intent.
* **@Controller:**  
  Used to mark a class as a web controller in a Spring MVC application. This makes the class eligible for handling HTTP requests, request mapping, and response rendering.

Example

```
@Repository
public class UserRepository { /* ... */ }

@Service
public class UserService { /* ... */ }

@Controller
public class UserController { /* ... */ }
```

Spring will automatically discover and manage these classes as beans based on their roles, thanks to the stereotype annotations.

Best Practices

* Use stereotype annotations to clearly define the role of each class.
* Favor @Component for generic components, and use @Repository, @Service, and @Controller for specific roles.
* Use @Bean for manual bean registration, not for marking classes.

* **DriverManager:**

* **JdbcTemplate:**  
  `JdbcTemplate` is a utility for running raw JDBC queries, not for ORM. It’s not necessary if you’re only using JPA.

Example: Spring Boot Configuration

```
@SpringBootApplication

public class User { /* ... */ }

@Repository
public interface UserRepository extends JpaRepository<User, Long> { }

With the right dependencies, Spring Boot will configure `DataSource` and `JpaTransactionManager` automatically.

Best Practices

* Always ensure a `DataSource` is available in your context (by providing database configuration).

Question: Which of these web-related types can be declared as parameters on a Spring MVC controller method and will be automatically provided by the framework?

**(A)** ServletRequest

**(B)** ApplicationContext

**(C)** HttpSession

**(D)** ServletResponse
### Explanation


Spring MVC lets you declare certain **web-related types** as parameters in your controller methods. For supported types, the framework automatically injects the corresponding servlet API objects, so you can work directly with the current HTTP request, response, or session.

Automatically injected web context types

**ServletRequest / HttpServletRequest**  
Gives you access to the current HTTP request: headers, parameters, attributes, etc.

```
@GetMapping("/example")
public String handleRequest(ServletRequest request) {
    String param = request.getParameter("foo");
    return "view";
}
```

**ServletResponse / HttpServletResponse**  
Allows you to work with the HTTP response: set status, headers, or write directly to the body.

```
@PostMapping("/submit")
public void handleResponse(ServletResponse response) throws IOException {
    response.getWriter().write("Hello, World!");
}
```

**HttpSession**  
Represents the user’s HTTP session and lets you store and retrieve session attributes.

```
@GetMapping("/session")
public String handleSession(HttpSession session) {
    session.setAttribute("key", "value");
    return "sessionView";
}
```

All three – `ServletRequest`, `ServletResponse`, and `HttpSession` – are valid controller method parameters that Spring will supply automatically.

What is *not* injected as a method parameter

**ApplicationContext** is **not** injected as a controller method parameter.  
It is the central Spring container managing all beans and configuration, not a per-request web object. If you need it, you obtain it via normal dependency injection (e.g. constructor injection or `@Autowired`), not as a handler method argument.

Best practice

Use these low-level servlet types only when you really need direct access to the HTTP layer. For most cases, prefer higher-level Spring MVC features like `@RequestParam`, `@PathVariable`, `@RequestBody`, `Model`, etc., which keep your controllers cleaner and easier to test.

### Question


Question: In the context of Spring AOP, what is a pointcut?

**(A)** a parameter that every advice method must specify in its signature that provides access to the execution context

**(B)** a predicate used to identify join points

**(C)** an expression to identify methods to which the advice applies to

**(D)** A configuration class that defines the aspects in a Spring application
### Explanation


What Exactly *Is* a Pointcut?

In Aspect-Oriented Programming a **pointcut** tells the AOP framework *where* to apply cross-cutting logic.  
In Spring AOP:

1. **Predicate Over Join Points** – A pointcut acts as a boolean test evaluated against every join point (in Spring, every method execution).
2. **Declared via Expressions** – You define the predicate using AspectJ-style expressions such as `execution(* com.example.service.*.*(..))`.
3. **Combined with Advice** – A pointcut alone does nothing; it must be paired with advice (`@Before`, `@After`, `@Around`, etc.). The advice executes whenever the predicate matches.

```
@Aspect
public class LoggingAspect {

    // pointcut definition
    @Pointcut("execution(* com.example.service.*.*(..))")
    private void serviceLayer() {}

    // advice using the pointcut
    @Before("serviceLayer()")
    public void log(JoinPoint jp) {
        System.out.println("Calling: " + jp.getSignature());
    }
}
```

Here, `serviceLayer()` is a named pointcut. Whenever any method in `com.example.service` is invoked, the `log` advice runs.

Why It Matters

* **Separation of Concerns** – Your business code stays clean; logging, security or transaction logic is isolated in aspects.
* **Fine-Grained Control** – By tweaking the pointcut expression you can target exactly the components you want, down to package, class, method name, parameters or annotations.
* **Reusability** – Named pointcuts can be referenced by multiple advice methods, promoting DRY principles.

Best Practice Tips

* Keep pointcut expressions readable—break complex expressions into named pointcuts.
* Prefer annotation-based pointcuts (e.g., `@annotation(…)`) when targeting specific concerns like security roles.
* Remember that Spring AOP is proxy-based: only public methods of Spring-managed beans are intercepted.

* **Dirty reads**: A transaction reads data that has been modified but not yet committed by another transaction.
* **Non-repeatable reads**: A transaction reads the same row twice and gets different results because another transaction modified or deleted that row in the meantime.
* **Phantom reads**: A transaction executes the same query twice and finds new rows the second time because another transaction inserted data matching the query condition.

The **Read Committed** isolation level prevents dirty reads by ensuring that only committed data can be read. However, it still allows non-repeatable reads and phantom reads since other transactions may change or insert data during the current transaction.

Other levels provide stronger guarantees:

* **Read Uncommitted** allows dirty reads.
* **Repeatable Read** prevents dirty reads and non-repeatable reads but not phantom reads.
* **Serializable** prevents all three anomalies, ensuring the strictest isolation but at the cost of performance.

Thus, the correct answer is **Read Committed**, because it specifically prevents dirty reads while still allowing the other two anomalies.

Question: Which of the following statements correctly describes how `@Transactional` behaves by default in Spring?

**(A)** It rolls back the transaction for both checked and unchecked exceptions by default.

The `@Transactional` annotation in Spring is a powerful mechanism that simplifies transaction management in enterprise applications. It allows you to declaratively manage transaction boundaries without dealing with boilerplate code. Here's what every Spring developer should understand about its default behavior:

**1. What Is** `@Transactional`**?**

`@Transactional` is an annotation provided by Spring to declaratively demarcate transaction boundaries. When applied to a method or class, it ensures that the method runs within a transactional context. If any failure occurs that meets rollback criteria, the entire transaction is rolled back automatically.

**2. Rollback Rules – Default Behavior**

By default, Spring's transaction management rolls back transactions **only for unchecked exceptions**, which means:

* **Rollback will occur** if the method throws:

  + Any subclass of `RuntimeException` (e.g. `IllegalArgumentException`, `NullPointerException`)
  + Any subclass of `Error` (e.g. `OutOfMemoryError`, `StackOverflowError`)
* **Rollback will NOT occur** if the method throws:

  + Checked exceptions like `IOException`, `SQLException`, or custom checked exceptions

This default behavior is designed to prevent rollbacks on common recoverable exceptions unless explicitly requested. If you need to roll back on a checked exception, you must specify it explicitly using the `rollbackFor` attribute:

```
@Transactional(rollbackFor = IOException.class)
public void processFile() throws IOException {
    // Will trigger rollback on IOException
}
```

Similarly, if you want to avoid rollback for a specific exception, you can use `noRollbackFor`:

```
@Transactional(noRollbackFor = IllegalArgumentException.class)
public void doSomething() {
    throw new IllegalArgumentException("Will not cause rollback");
}
```

**3. Transaction Propagation – Default Behavior**

The default propagation setting for `@Transactional` is `REQUIRED`.

This means:

* If a transaction is already in progress, the method joins that existing transaction.
* If no transaction is active, a new one is created.

This behavior ensures seamless nesting of transactional methods. However, if you need to always run a method in a new transaction, regardless of the current context, you can use:

```
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void independentOperation() {
    // Always runs in a new transaction
}
```

There are several other propagation levels, such as `MANDATORY`, `SUPPORTS`, `NESTED`, each with specific behavior depending on transaction presence. These are useful in complex transactional flows.

**4. Where Should** `@Transactional` **Be Applied?**

`@Transactional` is typically applied to methods in the **service layer**. This layer is responsible for coordinating business logic and database operations, making it the ideal place for transaction boundaries.

You can annotate either the method or the entire class:

```
@Service
@Transactional
public class OrderService {
    public void createOrder() {
        // This method runs within a transaction
    }
}
```

If applied at the class level, all **public** methods of the class will be transactional. Private methods are **never** affected by `@Transactional`.

**5. Self-Invocation Limitation**

A very important nuance is that **method calls within the same class bypass transactional proxies**. This means if a transactional method is called from another method in the same class, it won’t go through the Spring proxy, and the transactional behavior won’t be applied.

**Incorrect:**

```
@Transactional
public void methodA() {
    methodB(); // This does NOT go through the proxy!
}

@Transactional
public void methodB() {
    // Will not be transactional
}
```

**Correct workaround:** Retrieve the proxy from the Spring context:

```
@Autowired
private ApplicationContext context;

public void methodA() {
    context.getBean(getClass()).methodB(); // Goes through proxy, so transactional
}
```

**6. Read-Only Transactions**

For methods that only **read data** (without modifying it), you can optimize performance using:

```
@Transactional(readOnly = true)
public List<User> findAllUsers() {
    return userRepository.findAll();
}
```

This hints to the underlying transaction manager that the method will not perform updates, allowing certain optimizations at the database or persistence provider level (e.g. disabling dirty tracking in Hibernate).

**7. Nested Transactions**

Spring supports **nested transactions** using `Propagation.NESTED`. This is useful when you want a sub-operation to run in its own transaction, but still be part of a parent transaction’s scope.

```
@Transactional
public void parentMethod() {
    childMethod(); // Runs in a nested transaction
}

@Transactional(propagation = Propagation.NESTED)
public void childMethod() {
    // Can rollback independently
}
```

Be aware that **nested transactions require support from the underlying transaction manager**, such as JDBC savepoints.

**8. Transaction Manager Configuration**

In most Spring Boot applications, the transaction manager is automatically configured based on the database used (e.g. `DataSourceTransactionManager` for JDBC, `JpaTransactionManager` for JPA/Hibernate).

You can still define it explicitly if needed:

```
@Bean
public PlatformTransactionManager transactionManager(EntityManagerFactory emf) {
    return new JpaTransactionManager(emf);
}
```

**Conclusion**

Understanding how `@Transactional` behaves by default in Spring is crucial for ensuring **data integrity**, **performance**, and **predictable error handling**. It allows you to declaratively define transaction boundaries without cluttering your business logic with boilerplate code. By mastering its configuration and limitations, you'll write safer, more reliable applications that scale cleanly.

**(B)** unchecked exception

**(C)** checked exception

**(D)** java.lang.Error
### Explanation


In Spring’s transaction management model, the default rollback rules are tied to the type of exception thrown during transactional execution. By default:

* **Unchecked exceptions (**`RuntimeException` **and its subclasses)** cause a rollback.

  + Example: `NullPointerException`, `IllegalArgumentException`.
  + These are considered programming or system-level errors that indicate something unexpected and critical happened.
* `Error` **(and its subclasses)** also cause a rollback.

  + Example: `OutOfMemoryError`.
  + Errors represent serious conditions that applications are usually not expected to recover from, so Spring rolls back to maintain consistency.
* **Checked exceptions (any exception that does not extend** `RuntimeException`**)** do **not** trigger a rollback by default.

  + Example: `IOException`, `SQLException`.
  + The assumption is that these exceptions represent recoverable conditions, and rollback should be decided explicitly.

This behavior can be customized using the `@Transactional` annotation:

```
@Transactional(rollbackFor = IOException.class)
public void processFile() throws IOException {
    // method logic
}
```

Here, even though `IOException` is a checked exception, Spring is instructed to roll back the transaction when it occurs.

This rollback policy provides a balance between **convenience** (automatic rollback on critical/unexpected issues) and **flexibility** (developers can fine-tune rollback behavior for checked exceptions when needed).

### Question


Question: What one of these ensures that if anything goes wrong, the changes will be preserved once the system is back?

**(A)** Atomicity

**(B)** Consistency

**(C)** Isolation

**(D)** Durability
### Explanation


This question touches on the **ACID properties** of transactions, which are fundamental to reliable data management in relational databases and transactional systems. Understanding ACID is essential for any Spring Certified Professional since Spring provides comprehensive transaction management through `@Transactional` and `PlatformTransactionManager`.

1. **Atomicity**

   * *All-or-nothing principle*.
   * Either the entire transaction succeeds (all statements committed) or none of it does (rollback).
   * Prevents partial updates but does **not guarantee persistence after system crash**.
2. **Consistency**

   * Ensures that a transaction brings the database from one valid state to another.
   * Enforces constraints (foreign keys, unique keys, domain rules).
   * Important for integrity but unrelated to crash recovery.
3. **Isolation**

   * Controls how concurrent transactions interact.
   * Prevents dirty reads, phantom reads, and non-repeatable reads, depending on the isolation level.
   * Related to concurrency, not durability of committed data.
4. **Durability (Correct Answer)**

   * Guarantees that once a transaction is **committed**, the changes are **permanent** and survive crashes, power failures, or system restarts.
   * Implemented by the database using techniques like **write-ahead logs (WAL)**, transaction journals, and replication to ensure that data is not lost.
   * This is the **“preservation”** aspect of ACID.
5. **Spring Context**

   * In Spring, `@Transactional` ensures Atomicity, Consistency, and Isolation at the framework level.
   * **Durability** is guaranteed by the **underlying database engine** (e.g., PostgreSQL, MySQL, Oracle).
   * Spring does not implement durability itself—it relies on the database’s transaction manager to ensure committed data is permanent.
6. **Best Practices**

   * Always ensure that your database runs with durability guarantees (e.g., PostgreSQL with WAL enabled, MySQL with InnoDB).
   * For mission-critical systems, configure replication and backups to strengthen durability.
   * Avoid databases or storage engines that relax durability for performance (e.g., MySQL MyISAM).
7. **Exam Tip**

   * If the question mentions **preserving changes after failure**, the answer is always **Durability**.
   * If it mentions **all-or-nothing execution**, that’s **Atomicity**.
   * If it mentions **data integrity**, that’s **Consistency**.
   * If it mentions **concurrent execution without interference**, that’s **Isolation**.

**Suggestion:** In real-world Spring applications, never assume durability—validate that your database engine uses a durable storage mechanism and that it is configured properly (e.g., fsync, WAL, journaling). Spring guarantees transaction semantics at the application level, but durability lives in the database layer.

In Spring, **Dependency Injection (DI)** is the fundamental design principle that decouples object creation from object usage. Instead of classes instantiating their own dependencies, Spring injects them at runtime. This makes applications more modular, testable, and maintainable.

There are two main DI strategies supported by Spring:

1. **Constructor-based Dependency Injection**

   * Dependencies are provided through a class constructor.
   * Ensures that a bean is always created in a **fully initialized state** with all required dependencies.
   * Encourages **immutability** and makes testing easier because dependencies cannot be replaced accidentally.
   * Example:

     ```
     @Component
     public class OrderService {
         private final PaymentService paymentService;

         @Autowired
         public OrderService(PaymentService paymentService) {
             this.paymentService = paymentService;
         }
     }
     ```

2. **Setter-based Dependency Injection**

   * Dependencies are injected through setter methods.
   * Allows **optional** dependencies and makes beans mutable after creation.
   * Useful when a dependency is not strictly required for object construction.

     ```
     @Component
     public class NotificationService {
         private EmailService emailService;

         @Autowired
         public void setEmailService(EmailService emailService) {
             this.emailService = emailService;
         }
     }
     ```

   * Factory-based DI → ❌ Not a recognized style. While Spring does allow `FactoryBean`s, that is a different mechanism, not a DI pattern.

   * **Constructor injection is the default recommendation** (even more so since Spring 4.3, which allows omission of `@Autowired` if there is a single constructor).
   * Use **Lombok’s** `@RequiredArgsConstructor` to reduce boilerplate when injecting via constructor.
   * Avoid field injection (`@Autowired` directly on fields) in production code—it makes testing and immutability harder.
5. **Exam Tip**

   * Correct answer: **Constructor-based DI** and **Setter-based DI**.
   * If you see “getter-based” or “factory-based” as options, they are distractors.

**Suggestion:** Always design your beans with **constructor injection** as the default. Reserve setter injection only for optional dependencies. This ensures better encapsulation, immutability, and avoids `NullPointerException` risks in your Spring applications.

In Spring, transactions are managed via `@Transactional`.    * **Hibernate optimization**: Hibernate can skip unnecessary **dirty checking** (the process of comparing loaded entities against the database to detect changes before flushing). This reduces overhead when dealing with large result sets.

   * It does **not prevent update statements** from executing. If your code executes a modifying query inside a read-only transaction, the DB will still perform the update.
   * It is **not mandatory** for Hibernate or Spring—transactions work without it. It’s purely an optimization.
3. **Use Cases**

   * Service-layer methods that only perform **read operations** (`findAll`, `findById`, reporting queries).
   * Long-running queries with large result sets, where dirty checking overhead can degrade performance.
4. **Best Practices**

   * Use `@Transactional(readOnly = true)` on query-oriented service methods.
   * Combine it with `@Repository` or service-layer beans where JPA queries are executed.
   * Do not assume it enforces immutability—developers must still avoid executing updates.
   * Always leave write transactions as the default (`readOnly = false`).
5. **Exam Tip**

   * Correct reasons: **performance optimizations** (skipping flush/dirty checking).
   * Wrong reasons: “mandatory with Hibernate” or “prevents modifications.”
   * Remember: `readOnly` **is an optimization hint, not a security guardrail.**

**Suggestion:** Always annotate read-only service methods with `@Transactional(readOnly = true)` in Hibernate-based projects. It reduces flush overhead, improves performance, and makes intent explicit. For critical write operations, keep standard `@Transactional` without `readOnly`.

### Question


Question: Which of the following best describes the behavior of the HTTP PUT method?

**(A)** Replaces an existing resource or creates a new resource if it does not exist

**(B)** Sends data to the server to partially update a resource

**(C)** Deletes a specified resource on the server

**(D)** Sends data to the server, usually leading to changes or resource creation
### Explanation


The **HTTP PUT** method is one of the core RESTful verbs and has very specific semantics that distinguish it from **POST** and **PATCH**. Understanding its behavior and idempotency is key for REST API design and for the Spring exam.

1. **Behavior of PUT (Correct)**

   * **Replaces** the target resource with the payload provided.
   * If the resource does **not exist**, it can be **created** at the given URI.
   * Example:

     ```
     PUT /users/123
     { "id": 123, "name": "mk", "role": "ADMIN" }
     ```

     + If `/users/123` exists → it is completely replaced.
     + If `/users/123` does not exist → it is created.
2. **Idempotency**

   * PUT is **idempotent**: multiple identical PUT requests have the same effect as one.
   * Example: calling PUT `/users/123` with the same payload three times produces the same final state.
3. **What PUT is NOT**

   * Not for **partial updates** → use **PATCH** instead.
   * Not for **creating new resources without specifying the URI** → that’s **POST**.
   * Not for **deletion** → that’s **DELETE**.
4. **Best Practices**

   * Use PUT when the **client knows the full URI** of the resource and wants to fully replace it.
   * Use POST for **creating new resources** where the server decides the identifier.
   * Use PATCH for **partial updates** (e.g., updating just one field of an object).
   * Ensure PUT handlers in Spring controllers are idempotent and replace the entire resource:

     ```
     @PutMapping("/users/{id}")
     public ResponseEntity<UserDto> updateUser(@PathVariable Long id, @RequestBody UserDto dto) {
         UserDto updated = userService.replaceUser(id, dto);
         return ResponseEntity.ok(updated);
     }
     ```
5. **Exam Tip**

   * PUT = **Replace or Create** + **Idempotent**.
   * POST = **Create** + **Non-idempotent**.
   * PATCH = **Partial update**.
   * DELETE = **Remove**.

**Suggestion:** In real REST APIs, reserve **PUT for full resource replacement** and ensure idempotency. For updates where only a subset of fields change, always use **PATCH** to avoid confusion and wasted payload transfers.

### Question


Question: ```

@Component
public class Dog implements IAnimal {}

@Component
public class Cat implements IAnimal {}

@Component
public class Person {
    @Autowired
    private IAnimal animal;
}
```

**(B)** Use the @Primary annotation on one of the classes

**(C)** Use @Qualifier("animal") on top of Dog or Cat

**(D)** Add  @Qualifier("cat") on IAnimal animal field

When multiple beans match a single injection point by **type**, Spring can’t choose automatically. Here, `IAnimal` has two candidates: `Dog` and `Cat`. You resolve the ambiguity by either declaring a **primary** bean or **qualifying** the target bean.

1. **@Primary (type preference)**

   * Mark exactly one candidate as the default for that type:

     ```
     @Component
     @Primary
     class Cat implements IAnimal {}
     ```
   * Any `@Autowired IAnimal` without qualifiers now injects `Cat`.
   * Works only if there’s exactly one `@Primary` per type (otherwise another conflict).
2. **@Qualifier (name preference)**

   * Specify the exact bean to inject:

     ```
     @Component
     class Cat implements IAnimal {}

     @Component
     class Person {
       @Autowired
       @Qualifier("cat") // bean name is class name decapitalized by default
       private IAnimal animal;
     }
     ```

   * Constructor injection with `@Qualifier`:

     ```
     @Component
     class Person {
       Person(@Qualifier("cat") IAnimal animal) { ... }
     }
     ```
   * Java config with `@Bean` names works similarly with qualifiers.

**Exam takeaway:** Use `@Primary` to set a default candidate; use `@Qualifier` on the injection point to pick a specific bean. Changing the field name doesn’t influence `@Autowired`.

**Suggestion:** Prefer **constructor injection** and use `@Qualifier` at the constructor parameter for clarity and testability; reserve `@Primary` for a sensible default across the app.

   * Cannot prevent execution, but can prepare context (e.g., logging, security checks).

   * **Transaction** = a database-level concept ensuring ACID properties.

   * **Query** → read-only operation, no transactional semantics.
   * **Request** → a generic interaction, doesn’t imply atomicity.

   * In Spring, `@Transactional` relies on the **Unit of Work** pattern behind the scenes (via persistence providers like Hibernate).
   * Example:

     ```
     @Transactional
     public void registerUser(User user) {
         userRepository.save(user);
         profileRepository.createProfile(user);
         // Both changes succeed or both rollback
     }
     ```
5. **Best Practices**

   * Treat business use cases (e.g., “place order”, “register user”) as the boundary for your Unit of Work.
   * Don’t span Units of Work across multiple service calls or remote calls—keep them local and consistent.
   * Use ORM-provided UoW (Hibernate, JPA) instead of rolling your own.
6. **Exam Tip**

   * If the question is about **design pattern** → answer is **Unit of Work**.
   * If it’s about **database behavior** → answer is **Transaction**.

     + It cannot proxy final methods.
     + It uses JDK Dynamic Proxies by default.
   * Incorrect statements:

     + "Spring uses AspectJ annotations only" → misleading, Spring provides its own.
     + "Spring AOP applies aspects at compile time" → false, that’s AspectJ.

**Suggestion:** In production, **design service beans with interfaces** — this makes proxying predictable and aligns with best practices (clean layering, easier mocking in tests). Use AspectJ only if you hit Spring AOP’s proxy limitations.

## Question #140

### Question


Question: Can the `@Bean` annotation be used together with the `@Profile` annotation in Spring Framework?

**(A)** yes

**(B)** no
### Explanation


This is a common and recommended practice when you want to register beans only for specific environments (profiles).

1. **How It Works**

   * `@Bean` → Declares a bean method inside a `@Configuration` class.
   * `@Profile` → Restricts the bean’s registration to specific active profiles.
   * Together, this means Spring will only create that bean when the matching profile is active.

   Example:

   ```
   @Configuration
   public class DataSourceConfig {

       @Bean
       @Profile("dev")
       public DataSource devDataSource() {
           return new HikariDataSource(devConfig());
       }

       @Bean
       @Profile("prod")
       public DataSource prodDataSource() {
           return new HikariDataSource(prodConfig());
       }
   }
   ```

   * If `spring.profiles.active=dev`, only `devDataSource` is registered.
   * If `spring.profiles.active=prod`, only `prodDataSource` is registered.
2. **Alternative Usage**

   * `@Profile` can also be applied at the **class level** to include/exclude an entire `@Configuration` class based on active profiles.
3. **Best Practices**

   * Use `@Profile` to cleanly separate environment-specific beans (dev, test, staging, prod).
   * Keep environment differences in configuration classes rather than scattering `if` conditions across your code.
   * Use `application-{profile}.properties` for configuration differences and `@Profile` for **bean wiring differences**.

## Question #141

### Question


Question: JdbcTemplate in Spring Framework is an example of which design pattern?

**(A)** Template

**(B)** Adapter

**(C)** Factory

**(D)** Decorator

**(E)** Singleton
### Explanation


`JdbcTemplate` in Spring Framework is a textbook example of the **Template Method design pattern**.

1. **Why Template Method?**

   * JDBC code is notoriously verbose: opening connections, preparing statements, handling exceptions, closing resources.
   * The **invariant part** of the workflow (connection management, exception translation, resource cleanup) is implemented by `JdbcTemplate`.
   * The **variable part** (the actual SQL, parameters, and result set mapping) is delegated to callbacks such as `RowMapper`, `ResultSetExtractor`, or `PreparedStatementSetter`.
   * This is exactly how the Template Method pattern works: a **fixed algorithm skeleton** with pluggable steps provided by the client.

   Example:

   ```
   List<User> users = jdbcTemplate.query(
       "SELECT id, name FROM users",
       (rs, rowNum) -> new User(rs.getLong("id"), rs.getString("name"))
   );
   ```

   * The template handles connection lifecycle, exceptions, closing resources.
   * You only implement the "mapping" step.
2. **Why Not Other Patterns?**

   * **Adapter** → Adapts one interface to another (not the case here).
   * **Factory** → Creates objects (not the case, JdbcTemplate executes logic).
   * **Decorator** → Wraps functionality without changing interface (not the case).
   * **Singleton** → A scope/lifecycle concept, not the inherent pattern of `JdbcTemplate`.
3. **Best Practices**

   * Always use `JdbcTemplate` instead of raw JDBC for better readability, safety, and exception translation.
   * Use `NamedParameterJdbcTemplate` for improved readability when dealing with multiple query parameters.
   * Prefer Spring Data JPA for complex persistence needs, but fall back to `JdbcTemplate` when you need direct SQL control.

### Question


Question: Which of the following URLs is used to access the available actuator endpoints in a Spring Boot application with the default configuration? Assume the application is running on port 8080.

**(A)** http://localhost:8080/actuator

**(B)** http://localhost:8080/bootactuator

**(C)** http://localhost:8080/boot/actuator

**(D)** http://localhost:8080/endpoint/actuator
### Explanation


Spring Boot provides the **Actuator module** for exposing operational endpoints — things like health checks, metrics, environment info, thread dumps, and more. These endpoints are extremely useful for monitoring and managing applications in production.

1. **Default Base Path**

   * By default, all actuator endpoints are exposed under:

     ```
     http://localhost:8080/actuator
     ```
   * This base path is configurable via:

     ```
     management.endpoints.web.base-path=/manage
     ```

     If you change it, endpoints will be available under `/manage` instead of `/actuator`.
2. **Available Endpoints**

   * With the starter added (`spring-boot-starter-actuator`), endpoints are auto-configured.
   * Examples:

     + `/actuator/health` → Health status (exposed by default).
     + `/actuator/info` → Application info (metadata, version, build info).
     + `/actuator/metrics` → Metrics (memory, threads, custom metrics).
     + `/actuator/env` → Environment properties.
3. **Exposure Settings**

   * By default, only `/health` and `/info` are exposed over HTTP.
   * To expose more endpoints:

     ```
     management.endpoints.web.exposure.include=*
     ```
   * Or restrict explicitly:

     ```
     management.endpoints.web.exposure.include=health,info,metrics
     management.endpoints.web.exposure.exclude=env
     ```
4. **Security Considerations**

   * Actuator endpoints may expose sensitive information.
   * In production, secure them with **Spring Security** and limit exposure to trusted networks.
5. **Exam Tip**

   * Default URL → `http://localhost:8080/actuator`.
   * If a question mentions `/bootactuator`, `/boot/actuator`, or `/endpoint/actuator`, those are **wrong**.
   * Always remember: base path = `/actuator`, unless changed in properties.

**Suggestion:** In production, expose only necessary actuator endpoints (like `health` and `info`), secure them via Spring Security, and integrate with monitoring tools (Prometheus, Grafana, ELK).
