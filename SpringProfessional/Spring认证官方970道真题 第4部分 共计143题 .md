   * Spring integrates with various transaction managers (e.g., `DataSourceTransactionManager`, `JpaTransactionManager`) to manage the underlying database transactions.
   * The transaction manager is responsible for coordinating the transaction with the database.
4. **How AOP Works in Transaction Management:**

   * The proxy ensures that the transactional context is applied to the method execution.

Question: Which of the following statements correctly describes the `REPEATABLE_READ` isolation level in database transactions?

**(A)** Dirty, repeatable, and phantom reads are entirely prevented when a transaction operates at this isolation level.

**(B)** Dirty reads are permitted when a transaction operates at this isolation level.

**(C)** Repeatable reads may occur when a transaction operates at this isolation level.

**(D)** Phantom reads are possible when a transaction operates at this isolation level.
### Explanation


The `REPEATABLE_READ` **isolation level** is a standard isolation level in SQL that ensures a balance between data consistency and performance. It provides the following guarantees:

1. **Prevention of Dirty Reads:**

   * Dirty reads are prevented, meaning that a transaction cannot read uncommitted changes made by another transaction.
2. **Guarantee of Repeatable Reads:**

   * Repeatable reads are guaranteed, ensuring that multiple reads of the same data within a transaction return consistent results, even if other transactions modify the data.
3. **Possibility of Phantom Reads:**

   * Phantom reads remain possible. Phantom reads occur when a query retrieves a set of rows that satisfy a condition, and another transaction modifies the set (e.g., by inserting or deleting rows). When the query is re-executed within the same transaction, the results may differ.

**Przykład Phantom Reads:**

1. **Transaction 1:**

   ```
   sqlSELECT * FROM employees WHERE department_id = 10;
   ```
2. **Transaction 2:**

   ```
   sqlINSERT INTO employees (id, name, department_id) VALUES (101, 'John', 10);
   ```
3. **Transaction 1 (Re-executing the query):**

   ```
   sqlSELECT * FROM employees WHERE department_id = 10;
   ```

   * In this case, the second execution of the query in Transaction 1 may return a different result due to the new row inserted by Transaction 2.

**Porównanie poziomów izolacji:**

```
Isolation Level	    Dirty Reads	    Non-Repeatable Reads    Phantom Reads
READ_UNCOMMITTED    Possible	    Possible	            Possible
READ_COMMITTED	    Not Possible    Possible	            Possible
REPEATABLE_READ	    Not Possible    Not Possible	    Possible
SERIALIZABLE	    Not Possible    Not Possible	    Not Possible
```

Question: Which of the following statements about JPA and Hibernate caching mechanisms are correct?

**(A)** The first-level cache is associated with the EntityManager and is enabled by default.

**(B)** The second-level cache is shared across sessions and requires explicit configuration.

**(C)** The first-level cache can be disabled by setting the hibernate.cache.use_first_level_cache property to false.

**(D)** The second-level cache is enabled by default in Hibernate.
### Explanation


In JPA and Hibernate, caching mechanisms are used to optimize database access by reducing the number of queries sent to the database. Hibernate supports two levels of caching: **first-level cache** and **second-level cache**.

**Key Features of the First-Level Cache:**

1. **Scope:**

   * The first-level cache is associated with the `EntityManager` (or `Session` in Hibernate).
   * It is active for the duration of the `EntityManager` or `Session` lifecycle.
2. **Behavior:**

   * When an entity is accessed for the first time, it is fetched from the database and stored in the first-level cache.
   * Subsequent access to the same entity within the same transaction retrieves the entity from the cache instead of querying the database again.
3. **Mandatory:**

   * The first-level cache is always enabled and cannot be disabled.

**Key Features of the Second-Level Cache:**

1. **Scope:**

   * The second-level cache is shared across multiple `EntityManager` or `Session` instances.
   * It is designed to cache entities, collections, or query results for reuse across transactions.
2. **Configuration:**

   * The second-level cache is optional and must be explicitly enabled in the Hibernate configuration.
   * Example configuration in `hibernate.cfg.xml`:

     ```
     xml<property name="hibernate.cache.use_second_level_cache">true</property>
     <property name="hibernate.cache.region.factory_class">org.hibernate.cache.ehcache.EhCacheRegionFactory</property>
     ```
3. **Caching Providers:**

   * The second-level cache requires an external caching provider, such as Ehcache, Hazelcast, or Infinispan.
4. **Usage:**

   * Entities and collections must be explicitly marked as cacheable using the `@Cache` annotation or XML configuration.
   * Example:
```java
@Entity
     @Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
     public class Product {
         @Id
         private Long id;
         private String name;
     }
     ```

Question: What is the default rollback behavior of the @Transactional annotation in Spring?

**(A)** Spring rolls back the transaction for all exceptions, both checked and unchecked.

**(B)** Spring does not roll back the transaction for any exceptions by default.

**(C)** Spring rolls back the transaction for unchecked exceptions (RuntimeException) and Error by default.

**(D)** Spring rolls back the transaction for checked exceptions (Exception) by default.
### Explanation


In Spring, the `@Transactional` annotation is used to manage transactions declaratively. By default, Spring's transaction management has specific rules for rolling back transactions based on the type of exception thrown.

**Default Rollback Behavior:**

1. **Unchecked Exceptions (**`RuntimeException` **and** `Error`**):**

   * By default, Spring rolls back the transaction when an unchecked exception (subclass of `RuntimeException`) or an `Error` is thrown.
   * Example:
```java
@Transactional
     public void performTransaction() {
         throw new RuntimeException("This will trigger a rollback");
     }
     ```
2. **Checked Exceptions (**`Exception`**):**

   * By default, Spring does **not** roll back the transaction for checked exceptions (subclasses of `Exception`).
   * To enable rollback for checked exceptions, you must explicitly configure the `rollbackFor` attribute in the `@Transactional` annotation:
```java
@Transactional(rollbackFor = Exception.class)
     public void performTransaction() throws Exception {
         throw new Exception("This will trigger a rollback");
     }
     ```
3. **Customizing Rollback Behavior:**

   * You can customize the rollback behavior using the following attributes in the `@Transactional` annotation:

     + `rollbackFor`: Specifies the exception classes for which the transaction should be rolled back.
     + `noRollbackFor`: Specifies the exception classes for which the transaction should **not** be rolled back.

Question: Which of the following HTTP methods are idempotent?

**(A)** GET

**(B)** PUT

**(C)** POST

**(D)** DELETE
### Explanation


**Idempotency in HTTP:**  
Idempotency is a property of an operation where performing it multiple times has the same effect as performing it once. In the context of HTTP methods, idempotent methods ensure that repeated requests do not result in unintended side effects.

**Idempotent HTTP Methods:**

1. **GET:**

   * Used to retrieve data without modifying the state of the server.
   * Safe and idempotent.
2. **PUT:**

   * Used to create or update a resource.
   * Repeating the request with the same payload will result in the same state on the server.
3. **DELETE:**

   * Used to delete a resource.
   * Repeating the request will ensure the resource is deleted without additional side effects.

**Non-Idempotent HTTP Methods:**

1. **POST:**

   * Used to create resources or perform operations that may have side effects.
   * Repeating the request can result in different outcomes (e.g., creating multiple resources).
2. **PATCH:**

   * Used to partially update a resource.
   * The outcome may depend on the current state of the resource, making it non-idempotent.

```java
private MockMvc mockMvc;
     ```

**(B)** Read committed

**(C)** Read uncommitted

**(D)** Repeatable Reads
### Explanation


**What is Isolation in Transactions?**  
Isolation is one of the ACID (Atomicity, Consistency, Isolation, Durability) properties of database transactions. It defines how transaction operations are isolated from one another to ensure data consistency in concurrent environments.

**Isolation Levels in Order of Strictness:**

1. **Serializable (Highest):**

   * Prevents dirty reads, non-repeatable reads, and phantom reads.
   * Ensures that transactions are executed sequentially, as if they were serialized.
   * Provides the highest level of consistency but has the most significant performance impact due to locking or other concurrency control mechanisms.
2. **Repeatable Reads:**

   * Prevents dirty reads and non-repeatable reads.
   * Allows phantom reads (new rows added by other transactions may appear during the transaction).
   * Suitable for scenarios where consistency of repeated reads is required.
3. **Read Committed:**

   * Prevents dirty reads (only committed data can be read).
   * Allows non-repeatable reads and phantom reads.
   * Commonly used as the default isolation level in many database systems like PostgreSQL.
4. **Read Uncommitted (Lowest):**

   * Allows dirty reads, non-repeatable reads, and phantom reads.
   * Provides the least consistency but the highest performance.
   * Rarely used in practice due to potential data inconsistencies.

**Best Practices for Choosing Isolation Levels:**

1. **Understand Application Requirements:**

   * Choose the isolation level based on the application's consistency and performance needs. For example:

     + Use `Serializable` for financial transactions where absolute consistency is critical.
     + Use `Read committed` for applications where performance is more important than preventing phantom reads.
2. **Avoid Overhead Where Possible:**

   * Higher isolation levels like `Serializable` can lead to significant performance overhead due to locking or blocking. Use them only when necessary.
3. **Test for Concurrency Issues:**

   * Test the application under concurrent load to identify potential issues like deadlocks or performance bottlenecks caused by high isolation levels.
4. **Use Default Isolation Levels When Appropriate:**

   * Many databases use `Read committed` as the default isolation level, which is suitable for most applications.

**What is CGLIB Proxy?**  
CGLIB (Code Generation Library) is a library used by Spring for creating proxies of classes. Unlike JDK dynamic proxies, which require an interface, CGLIB proxies work by subclassing the target class. This allows proxying of classes without interfaces, but it comes with certain limitations.

**Key Features of CGLIB Proxy:**

1. **Subclassing Mechanism:**

   * CGLIB creates a subclass of the target class at runtime and overrides its methods to add proxy behavior.
2. **No Interface Required:**

   * Unlike JDK dynamic proxies, CGLIB proxies do not require the target class to implement an interface.
3. **Limitations:**

   * CGLIB proxies cannot intercept final methods because final methods cannot be overridden in subclasses.
   * CGLIB proxies do not intercept private methods because they are not accessible to subclasses.
4. **Self-Invocation Limitation:**

   * Like JDK dynamic proxies, CGLIB proxies do not support self-invocation. When a method in the same class calls another proxied method, the proxy is bypassed, and the call is made directly to the target method.
5. **Default Behavior in Spring:**

   * Spring uses JDK dynamic proxies by default if the target class implements at least one interface.
   * CGLIB proxies are used if the target class does not implement any interfaces or if explicitly configured.

**Example:**

**CGLIB Proxy in Action:**

```

public class AppConfig {
}

@Component
public class MyService {
    public void publicMethod() {
        System.out.println("Public method");
        privateMethod(); // Self-invocation bypasses proxy
    }

    private void privateMethod() {
        System.out.println("Private method");
    }

    public final void finalMethod() {
        System.out.println("Final method");
    }
}
```

* **Self-Invocation Limitation:**  
  When `publicMethod()` calls `privateMethod()`, the proxy is bypassed, and the call is made directly to the target method.
* **Final Method Limitation:**

**Best Practices for Using CGLIB Proxies:**

1. **Use JDK Proxies When Possible:**

   * Prefer JDK dynamic proxies if the target class implements interfaces, as they are simpler and have fewer limitations.
2. **Avoid Final Methods in Target Classes:**

   * Avoid declaring methods as `final` if they need to be proxied.
3. **Be Aware of Self-Invocation:**

   * Avoid self-invocation of proxied methods. If necessary, refactor the code to call the method from another bean.
4. **Explicitly Configure Proxy Mechanism:**

   * Use the `@EnableAspectJAutoProxy(proxyTargetClass = true)` annotation or `proxyTargetClass` property in XML to force the use of CGLIB proxies if needed.

**1. What is Aspect-Oriented Programming (AOP)?**

Aspect-Oriented Programming (AOP) allows developers to **separate cross-cutting concerns** (like logging, security, or transaction management) from business logic. Instead of duplicating the same code across multiple classes, AOP applies behaviors **dynamically** at runtime.

**2. Key AOP Concepts:**

ConceptDescription**Aspect**A module that defines cross-cutting concerns (e.g., logging, transactions).**Join Point**A specific point in a program's execution (e.g., method call, exception handling).**Advice**The action taken at a join point (e.g., before, after, around a method execution).**Pointcut**A **predicate** that matches **join points** (e.g., "apply logging to all methods in the service layer").**Target Object**The object whose method is being advised (also called the proxied object).

**3. Example: Applying Logging with AOP**

Here’s how Spring AOP works in practice:

**Step 1: Define an Aspect**

```
@Aspect
@Component
public class LoggingAspect {

    @Before("execution(* com.example.service.*.*(..))")
    public void logBeforeMethodExecution(JoinPoint joinPoint) {
        System.out.println("Executing method: " + joinPoint.getSignature());
    }
}
```

```
@Service
public class UserService {

    }
}
```

**Step 3: Running the Application**

```

User created: Alice
```

* The **join point** occurs at `createUser()` execution.
* The **advice** logs method details **before execution**.

ExpressionDescription`execution(* com.example..*(..))`Matches all methods in `com.example` package.`execution(* com.example.service.UserService.*(..))`Matches all methods in `UserService` class.`within(com.example.service..*)`Matches all methods inside `service` package.`@annotation(org.springframework.transaction.annotation.Transactional)`Matches methods annotated with `@Transactional`.

**5. Best Practices for AOP in Spring**

✅ Always test **pointcuts carefully** to avoid unwanted method interceptions.

**General Guide to Bean Scopes in Spring**

**What Are Bean Scopes?**

Spring provides different bean scopes to define how long a bean exists and how it is managed within the application context.

**Common Bean Scopes in Spring**

* **Singleton (default scope)** ensures that only one instance of the bean exists in the Spring container. It is created at startup and shared for all requests.
* **Prototype** creates a new instance of the bean every time it is requested. Spring does not manage its lifecycle beyond initialization.
* **Request (Web Scope)** ensures a new instance is created for each HTTP request.
* **Session (Web Scope)** maintains a bean instance for the duration of a user session.
* **Application (Web Scope)** creates a single instance per `ServletContext`.

**Singleton vs. Prototype Scope**

A singleton bean is useful for **stateless components** such as services, repositories, and controllers, as they can be reused without side effects. A prototype bean is useful for **stateful objects**, such as UI components or objects with user-specific configurations, where a new instance is needed for each operation.

**Lifecycle Callbacks in Singleton vs. Prototype**

A singleton bean follows the full Spring lifecycle, including initialization and destruction callbacks. A prototype bean, however, only calls initialization callbacks like `@PostConstruct`, while destruction callbacks like `@PreDestroy` are ignored. This means that if a prototype bean has cleanup logic, it must be explicitly managed by the developer.

For example, a singleton bean with lifecycle callbacks:

```
@Component
public class SingletonBean {
    @PostConstruct
    public void init() {
        System.out.println("Singleton initialized");
    }

    @PreDestroy
    public void destroy() {
        System.out.println("Singleton destroyed");
    }
}
```

A prototype bean requires manual cleanup:

```
@Component
@Scope("prototype")
public class PrototypeBean {
    @PostConstruct
    public void init() {
        System.out.println("Prototype initialized");
    }

    @PreDestroy
    public void destroy() {
        System.out.println("Prototype destroyed"); // Will NOT be called automatically
    }
}
```

To ensure the cleanup method runs for a prototype bean, the developer must manually destroy it:

```
PrototypeBean prototype = applicationContext.getBean(PrototypeBean.class);
// Perform operations
((ConfigurableApplicationContext) applicationContext).getBeanFactory().destroyBean(prototype);
```

**Best Practices for Managing Bean Scopes**

* Use **singleton scope** for **stateless beans** such as service and repository components.
* Use **prototype scope** for **stateful beans** where a new instance is required for every request.
* Be aware that **Spring does not manage the destruction of prototype beans**, so cleanup must be handled manually.
* When using **request, session, or application scopes**, ensure the application runs within a web environment, as these scopes rely on HTTP request handling.

**General Guide to** `@Transactional` **in Spring**

**1. What is** `@Transactional`**?**

The `@Transactional` annotation is used in **Spring applications** to define **transactional boundaries**. It ensures that a method or class runs within a transaction, allowing rollback and commit operations.

**2. Key Features of** `@Transactional`

* **Ensures atomicity** – multiple database operations within a transaction succeed or fail together.
* **Rolls back on runtime exceptions** – by default, **only unchecked exceptions (**`RuntimeException`**) trigger rollback**.
* **Can specify rollback behavior** – allows defining specific exceptions that should or should not trigger rollback.
* **Supports propagation and isolation levels** – allows controlling **transaction propagation and concurrency behavior**.

**3. Common** `@Transactional` **Attributes**

* `rollbackFor` – Specifies exception types that should trigger rollback.

  ```
  @Transactional(rollbackFor = IOException.class)
  ```
* `noRollbackFor` – Specifies exception types that should **not** trigger rollback.

  ```
  @Transactional(noRollbackFor = NullPointerException.class)
  ```
* `isolation` – Defines **isolation level** (e.g., `READ_COMMITTED`, `SERIALIZABLE`).

  ```
  @Transactional(isolation = Isolation.READ_COMMITTED)
  ```
* `propagation` – Defines how transactions **propagate** when called inside another transaction.

  ```
  @Transactional(propagation = Propagation.REQUIRES_NEW)
  ```

**4. Best Practices for Using** `@Transactional`

✅ Use `@Transactional` on **service layer methods**, not on controllers.  
✅ **Do not use it on private or static methods** (Spring does not manage those).  
✅ **Explicitly define rollback rules for checked exceptions** if needed.  
✅ **Use** `@Transactional(readOnly = true)` **for read-only operations** to improve performance.  
✅ **Avoid opening transactions in loops**, as this can degrade performance.

Spring Expression Language (SpEL) is a powerful expression language integrated into the Spring Framework. SpEL was introduced in Spring 3 and is now widely used across Spring projects including Spring Core, Spring Security, Spring Data, and Spring Integration.

SpEL expressions can be used in multiple places:

* Inside annotations like `@Value`, `@Conditional`, or `@Cacheable`
* In XML-based configuration
* Programmatically using `ExpressionParser`
* Inside Spring Security expressions
* Inside Spring Data query definitions (`@Query` with `#{}`)

SpEL supports several types of literals:

* **String**: `'hello'`
* **Numeric**: `123`, `45.67`
* **Boolean**: `true`, `false`
* **Null**: `null`


SpEL allows accessing properties and invoking methods on objects or beans.

### Question


Question: Which of the following are valid transaction propagation values?

**(A)** PREFERED

**(B)** NOT_ALLOWED

**(C)** REQUIRED

**(D)** MANDATORY
### Explanation


Transaction Propagation in Spring

**Transaction propagation** defines how a method interacts with an existing **transactional context**.  
It determines whether a method should **run within an existing transaction**, **start a new one**, or **run without any transaction**.

Spring defines transaction propagation behavior through the `Propagation` enum in the `@Transactional` annotation.

Valid Propagation Types

1. `REQUIRED` (Default)

* If a transaction exists, the method **runs within it**.
* If no transaction exists, a **new one is created**.
* This is the **most commonly used** propagation type.

**Use Case:** Standard transactional service methods.

**Example:**

```
@Transactional(propagation = Propagation.REQUIRED)
public void processOrder() {
    // runs in existing transaction or creates a new one
}
```

2. `REQUIRES_NEW`

* Always **creates a new transaction**.
* If a transaction already exists, it is **suspended** until the new transaction completes.

**Use Case:** Logging or audit operations that should **commit independently** of the main transaction.

**Example:**

```
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void logEvent() {
    // always runs in a new, independent transaction
}
```

3. `MANDATORY`

* Requires an **existing transaction**.
* If no transaction exists, Spring throws an **IllegalTransactionStateException**.

**Use Case:** Methods that must be executed **within an active transaction**.

**Example:**

```
@Transactional(propagation = Propagation.MANDATORY)
public void updateInventory() {
    // must be called from within an active transaction
}
```

4. `SUPPORTS`

* Runs **within a transaction** if one exists.
* Runs **non-transactionally** if no transaction is present.

**Use Case:** Read-only operations that can function both with and without a transaction.

**Example:**

```
@Transactional(propagation = Propagation.SUPPORTS, readOnly = true)
public Product findProduct(Long id) {
    // runs in transaction if available, otherwise non-transactional
}
```

5. `NOT_SUPPORTED`

* Always runs **non-transactionally**.
* If a transaction exists, it is **suspended**.

**Use Case:** Operations that should **never run** within a transaction.

**Example:**

```
@Transactional(propagation = Propagation.NOT_SUPPORTED)
public void sendEmail() {
    // always runs outside of any transaction
}
```

6. `NEVER`

* Must run **without a transaction**.
* If a transaction exists, Spring throws an **IllegalTransactionStateException**.

**Use Case:** Methods that **explicitly forbid** a transactional context.

**Example:**

```
@Transactional(propagation = Propagation.NEVER)
public void performNonTransactionalTask() {
    // throws exception if called from within a transaction
}
```

7. `NESTED`

* Runs within a **nested transaction** if a transaction exists.
* If no transaction exists, behaves like `REQUIRED`.
* Nested transactions can **roll back independently** of the outer transaction.
* Requires **JDBC 3.0 savepoint support**.

**Use Case:** Partial rollback scenarios.

**Example:**

```
@Transactional(propagation = Propagation.NESTED)
public void processSubTask() {
    // can rollback independently within the outer transaction
}
```

How to Specify Propagation

```
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void myMethod() {
    // method logic
}
```

If you don’t specify propagation, Spring uses `Propagation.REQUIRED` by default.

Common Pitfalls

* **Self-invocation issue:** Calling a `@Transactional` method from within the same class **bypasses the proxy**, so propagation settings are **ignored**. Always call transactional methods **from another bean**.
* **Incorrect propagation choice:** Using `REQUIRES_NEW` unnecessarily can cause **performance overhead** due to transaction suspension and creation.

Summary

* Propagation defines **how methods participate in transactions**.
* `REQUIRED` is the default and most commonly used.
* Use `REQUIRES_NEW` for independent transactions.
* Use `MANDATORY` to enforce transactional context.
* Use `SUPPORTS`, `NOT_SUPPORTED`, or `NEVER` for non-transactional or conditional execution.
* Use `NESTED` for partial rollback scenarios with savepoints.

Question: Which database transaction isolation levels allow phantom reads to occur?

**(A)** Serializable

**(B)** Repeatable reads

**(C)** Read uncommitted

**(D)** Read committed
### Explanation


Transaction isolation levels determine how transactions interact with each other in a database system. Phantom reads occur when a transaction re-executes a query returning a set of rows that satisfy a search condition and finds that the set of rows satisfying the condition has changed due to another transaction committing during the first transaction's execution.

Isolation Levels (from lowest to highest):

1. **Read Uncommitted**

   * Allows dirty reads, non-repeatable reads, and phantom reads
   * Offers highest performance but lowest data consistency
2. **Read Committed**

   * Prevents dirty reads
   * Allows non-repeatable reads and phantom reads
   * Default in many databases (e.g., PostgreSQL, Oracle)
3. **Repeatable Read**

   * Prevents dirty reads and non-repeatable reads
   * Still allows phantom reads
   * Default in MySQL/InnoDB
4. **Serializable**

   * Prevents all concurrency phenomena
   * Highest isolation but lowest concurrency
   * May cause significant performance impact

In Spring, you can set the isolation level using:

```
@Transactional(isolation = Isolation.REPEATABLE_READ)
```

* **Typical Use Cases:**  
  Use `@Bean` for **third-party library classes**, **complex setup**, or **conditional bean creation**.  
  Use `@Component` for **your own Spring-managed classes**.
* **Multiplicity:**  
  `@Bean` can define **multiple beans of the same type** with different configurations, while `@Component` typically defines **one bean per class**.

### Question


Question: Is the following statement true or false? If JdbcTemplate is used with transaction the existing connection will be reused, until available.

**(A)** True

**(B)** False
### Explanation


JdbcTemplate and Transaction Connection Management

When using `JdbcTemplate` inside a **Spring-managed transaction**, Spring’s transaction infrastructure ensures that the **same database connection** is reused throughout the transaction’s lifetime. This mechanism is key to maintaining **ACID properties** and ensuring **consistent transactional behavior**.

**How Connection Reuse Works**

**1. Transaction Starts**

* When a method annotated with `@Transactional` is invoked, Spring’s `TransactionManager`:

  + Obtains a **connection** from the configured `DataSource`.
  + Stores this connection in a **ThreadLocal** variable (binding it to the current thread).
  + Sets `autoCommit = false` to manage commit/rollback manually.

**2. JdbcTemplate Operations**

* Each time `JdbcTemplate` executes a query, it calls:

  ```
  DataSourceUtils.getConnection(dataSource)
  ```
* `DataSourceUtils` checks the `ThreadLocal` for an **existing transactional connection**:

  + If found → the **same connection** is reused.
  + If not found → a **new connection** is fetched from the pool (non-transactional context).

**3. Transaction Completion**

* **On commit:**

  + All changes are committed.
  + The connection is closed (returned to the pool).
* **On rollback:**

  + All uncommitted changes are rolled back.
  + The connection is closed (returned to the pool).

**Example**

```
@Service
public class UserService {

    @Autowired
    private JdbcTemplate jdbcTemplate;

    @Transactional
    public void transferFunds(Long fromUserId, Long toUserId, BigDecimal amount) {

        // First query - gets connection from transaction
        jdbcTemplate.update(
            "UPDATE accounts SET balance = balance - ? WHERE user_id = ?",
            amount, fromUserId
        );

        // Second query - REUSES the same connection
        jdbcTemplate.update(
            "UPDATE accounts SET balance = balance + ? WHERE user_id = ?",
            amount, toUserId
        );

        // Both updates use the same connection and are part of one transaction
        // If any statement fails, the entire transaction rolls back
    }
}
```

**Why Connection Reuse Matters**

**Transaction Isolation**

All operations must share the same connection to maintain **isolation levels**.  
Different connections might not see each other’s uncommitted changes.

**Atomicity**

All updates must either **commit or roll back together**.  
This is only possible when all operations run on **the same connection**.

**Performance**

Connection reuse avoids repeated connection acquisition, improving **efficiency** and **reducing pool overhead**.

**Consistency**

All queries executed within the same transaction see a **consistent database state**.

**What Happens Without @Transactional**

* Each `JdbcTemplate` operation gets a **new connection** from the pool.
* Every operation **auto-commits** immediately.
* No connection reuse occurs.
* No transactional guarantees — operations become independent.

**Key Takeaways**

* Connection reuse in Spring transactions is **automatic**.
* Managed internally by `TransactionSynchronizationManager` and `DataSourceUtils`.
* It’s **essential for transactional integrity**, isolation, and atomicity.
* Developers don’t need to manage connections manually — Spring handles it seamlessly.

### Explanation


@Transactional Rollback Behavior

Understanding how `@Transactional` handles **exceptions** and **rollback** is essential for designing robust transaction management in Spring applications.

**Default Rollback Behavior**

**Rollback Triggers (by default):**

* `RuntimeException` **(unchecked):** ✅ Rolls back
* `Error` **(unchecked):** ✅ Rolls back
* `Exception` **(checked):** ❌ Does **not** roll back — transaction commits

**Why This Design?**

* **Checked exceptions** typically indicate *recoverable business errors* (e.g., validation failures, user mistakes).
* **Unchecked exceptions** usually indicate *programming or system errors* that require rollback.
* The design follows the principle:

  Checked = recoverable, Unchecked = fatal.

**Example of Default Behavior:**

```
@Transactional
public void defaultBehavior() {
    // Rolls back:
    throw new IllegalArgumentException();  // RuntimeException
    throw new NullPointerException();      // RuntimeException  
    throw new OutOfMemoryError();          // Error

    // Commits (does NOT roll back):
    throw new IOException();               // Checked Exception
    throw new SQLException();              // Checked Exception
}
```

**Customizing with** `rollbackFor`

You can **add** exceptions that should trigger rollback in addition to the default ones.

```
@Transactional(rollbackFor = {IOException.class, SQLException.class})
public void transferMoney() throws IOException, SQLException {
    throw new IOException();     // Rolls back (added via rollbackFor)
    throw new SQLException();    // Rolls back (added via rollbackFor)
    throw new RuntimeException(); // Still rolls back (default behavior)
}
```

✅ **Important:**  
`rollbackFor` **adds** to the default rollback behavior — it does **not replace** it.

**Customizing with** `noRollbackFor`

You can **exclude** specific exceptions from triggering rollback.

```
@Transactional(noRollbackFor = {IllegalArgumentException.class})
public void processOrder() {
    throw new IllegalArgumentException(); // Commits (excluded)
    throw new NullPointerException();     // Rolls back
    throw new RuntimeException();         // Rolls back
}
```

**Combining** `rollbackFor` **and** `noRollbackFor`

You can mix both to fine-tune rollback behavior.

```
@Transactional(
    rollbackFor = IOException.class,
    noRollbackFor = IllegalArgumentException.class
)
public void complexScenario() {
    throw new IOException();              // Rolls back (added)
    throw new IllegalArgumentException(); // Commits (excluded)
    throw new NullPointerException();     // Rolls back (default unchecked)
    throw new SQLException();             // Commits (default checked)
}
```

**String-Based Alternatives**

If the exception class is **not on the classpath**, you can use string-based configuration:

```
@Transactional(rollbackForClassName = {"java.io.IOException"})
```

**Common Misconceptions**

Myth Reality `rollbackFor` replaces default behavior ❌ It **adds** to it — unchecked exceptions still roll back Specifying `rollbackFor` for checked exceptions affects unchecked ❌ Unchecked behavior is unchanged All exceptions cause rollback ❌ Only unchecked exceptions do by default

**Best Practices**

* ✅ Explicitly specify `rollbackFor` for **checked exceptions** that indicate failure:

  ```
  @Transactional(rollbackFor = Exception.class)
  ```
* ⚠️ Use `noRollbackFor` **sparingly** — typically for business exceptions that should commit.

  ```
  @Transactional(noRollbackFor = BusinessValidationException.class)
  ```
* 🧾 Clearly **document** your transactional exception policy.
* 💡 Prefer **unchecked exceptions** for unrecoverable errors.

**Real-World Example**

```
@Transactional(rollbackFor = {IOException.class, SQLException.class})
public void processPayment(Payment payment) throws PaymentException {
    try {
        paymentRepository.save(payment);          // DB operation
        paymentGateway.charge(payment);           // May throw IOException
    } catch (IOException e) {
        // Rolls back (specified in rollbackFor)
        throw new PaymentException("Payment failed", e);
    } catch (BusinessValidationException e) {
        // If noRollbackFor includes this, transaction commits
        throw e;
    }
}
```

**Key Takeaways**

* Default rollback occurs for **unchecked exceptions only**.
* `rollbackFor` **adds** checked exceptions to the rollback list.
* `noRollbackFor` **excludes** exceptions that would otherwise cause rollback.
* Fine-tuning rollback behavior helps ensure **transactional integrity** while keeping business logic predictable.

Question: Which of the following is the default transaction propagation level, when using @Transactional?

**(A)** NEVER

**(B)** ALWAYS

**(C)** REQUIRED

**(D)** SUPPORTS
### Explanation


**General Explanation: Default Transaction Propagation — REQUIRED**

The `@Transactional` annotation in Spring uses `Propagation.REQUIRED` by default, which is the most practical and widely used transaction propagation mode. It provides a balance between flexibility and safety by joining an existing transaction if one exists, or creating a new one otherwise.

**All Transaction Propagation Levels**

**1. REQUIRED (Default) ✓**

* Joins the existing transaction or creates a new one if none exists.
* Most common and safest option for service methods.

**Example:**

```
@Transactional  // Equivalent to @Transactional(propagation = Propagation.REQUIRED)
public void updateUser(User user) {
    userRepository.save(user);
}
```

**2. REQUIRES\_NEW**

* Always creates a **new, independent transaction**.
* Suspends any existing transaction until this one completes.
* Common for operations like **logging** or **auditing** that must commit independently.

**Example:**

```
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void logEvent(Event event) {
    eventRepository.save(event);
}
```

**3. MANDATORY**

* Requires an **existing transaction**; throws an exception if none exists.
* Used when a method should **only** run within a transactional context.

**Example:**

```
@Transactional(propagation = Propagation.MANDATORY)
public void validateInventory(Order order) {
    // Must be called within an active transaction
}
```

**4. SUPPORTS**

* Joins an existing transaction if one exists; otherwise, runs **non-transactionally**.
* Ideal for **read-only** operations that can run safely with or without a transaction.

**Example:**

```
@Transactional(propagation = Propagation.SUPPORTS, readOnly = true)
public User findUser(Long id) {
    return userRepository.findById(id).orElse(null);
}
```

**5. NOT\_SUPPORTED**

* Always runs **outside** of a transaction.
* Suspends any existing transaction.
* Useful for **non-transactional tasks** like sending emails or notifications.

**Example:**

```
@Transactional(propagation = Propagation.NOT_SUPPORTED)
public void sendEmail(String to, String message) {
    // Should not participate in transactions
}
```

**6. NEVER**

* Must execute **without** a transaction.
* Throws an exception if a transaction is active.

**Example:**

```
@Transactional(propagation = Propagation.NEVER)
public void performNonTransactionalTask() {
    // Fails if called from a transactional method
}
```

**7. NESTED**

* Runs within a **nested transaction** if one exists; otherwise behaves like REQUIRED.
* Supports **partial rollbacks** within a larger transaction.
* Requires JDBC 3.0 savepoint support.

**Example:**

```
@Transactional(propagation = Propagation.NESTED)
public void processSubTask() {
    // Can roll back independently within parent transaction
}
```

**Why REQUIRED is the Default**

**Practical Default**

* Most service methods need transactions.
* Works for both isolated and nested calls.

**Safe Behavior**

* Maintains data consistency.
* Avoids accidental non-transactional writes.

**Simplicity**

* Eliminates repetitive configuration.
* Reduces risk of misconfiguration.

**Common Scenarios**

**Scenario 1: Default REQUIRED behavior**

```
@Service
public class OrderService {
    @Autowired private PaymentService paymentService;

    @Transactional
    public void placeOrder(Order order) {
        orderRepository.save(order);
        paymentService.processPayment(order); // Joins same transaction
    }
}

@Service
public class PaymentService {
    @Transactional
    public void processPayment(Order order) {
        paymentRepository.save(order.getPayment());
    }
}
```

➡ Both methods execute in the **same transaction** — they commit or roll back together.

**Scenario 2: Using REQUIRES\_NEW for independent logging**

```
@Service
public class OrderService {
    @Autowired private AuditService auditService;

    @Transactional
    public void placeOrder(Order order) {
        orderRepository.save(order);
        auditService.logOrder(order); // Runs in a separate transaction
    }
}

@Service
public class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logOrder(Order order) {
        auditRepository.save(new AuditLog(order));
    }
}
```

➡ If `placeOrder()` fails, the **audit log still commits**, since it runs in its own transaction.

**Common Misconceptions**

* ❌ **Myth:** All `@Service` methods need `@Transactional`.  
  ✅ **Reality:** Only data-modifying methods typically need transactions.
* ❌ **Myth:** SUPPORTS is the default.  
  ✅ **Reality:** REQUIRED is the default and safer choice.
* ❌ **Myth:** Nested @Transactional methods always create nested transactions.  
  ✅ **Reality:** With REQUIRED, nested calls **join the existing** transaction.

**Best Practices**

* Use **REQUIRED** for most data-modifying operations.
* Use **REQUIRES\_NEW** only for truly independent operations (e.g., logging, auditing).
* Use **MANDATORY** to enforce existing transaction context.
* Use **SUPPORTS** for read-only methods.
* Avoid **NEVER** and **NOT\_SUPPORTED** unless necessary.
* Document any **non-default propagation** choices.

**Key Takeaways**

* `REQUIRED` is the **default propagation type**.
* You rarely need to specify it explicitly.
* It either **joins** an existing transaction or **creates** a new one.
* There is **no** `ALWAYS` propagation in Spring.
* Choose other propagation levels only when a **specific transactional behavior** is required.

## Question #101

### Question


Question: What is a bean factory post processor bean?

**(A)** an infrastructure bean of a type that implements BeanFactoryPostProcessor

**(B)** an infrastructure bean that allows for custom modification of bean definitions

**(C)** an infrastructure bean that allows for custom modification of beans

**(D)** an infrastructure bean that processes beans after they are fully initialized and ready for use
### Explanation


**Understanding** `BeanFactoryPostProcessor`

`BeanFactoryPostProcessor` is a powerful Spring **infrastructure interface** that allows developers to **customize and modify bean definitions** before the Spring container instantiates any beans.

**Key Concepts**

**Bean Lifecycle Timing**

1. The Spring container loads bean definitions from `@Configuration` classes, XML files, or component scanning.
2. The method `postProcessBeanFactory()` is then invoked.
3. At this point, bean definitions can be **read, modified, or replaced**.
4. Only after this phase are the beans instantiated — based on the possibly modified definitions.
5. Finally, `BeanPostProcessor` beans (which work on instances) are applied.

**Purpose**

`BeanFactoryPostProcessor` is used to:

* Modify **bean definitions (**`BeanDefinition` **objects)** before beans are created
* Add or remove bean definitions dynamically
* Change **bean properties, scopes, or initialization methods**
* Register additional beans programmatically

**Interface Definition**

```
public interface BeanFactoryPostProcessor {
    void postProcessBeanFactory(ConfigurableListableBeanFactory beanFactory) throws BeansException;
}
```

**Common Use Cases**

**1. Property Placeholder Resolution**  
`PropertySourcesPlaceholderConfigurer` replaces `${...}` placeholders in bean definitions with actual property values.

**2. Custom Scope Registration**  
Used to register custom bean scopes (e.g. `thread`, `session`, or `refresh`).  
Examples: `SimpleThreadScope`, `RefreshScope`.

**3. Conditional Bean Registration**  
Add or remove beans based on runtime environment or configuration conditions.

**4. Bean Definition Modification**  
Programmatically modify metadata such as:

* Bean class
* Bean scope (`singleton`, `prototype`)
* Lazy initialization flag (`lazy-init`)
* Custom property values

**Built-in Implementations**

* `PropertySourcesPlaceholderConfigurer` – resolves `${...}` placeholders from property sources
* `PropertyOverrideConfigurer` – overrides bean property values from external property files
* `CustomEditorConfigurer` – registers custom property editors for type conversion

**Example: Custom** `BeanFactoryPostProcessor`

```
@Component
public class CustomBeanFactoryPostProcessor implements BeanFactoryPostProcessor {

    @Override
    public void postProcessBeanFactory(ConfigurableListableBeanFactory beanFactory) {
        // Access an existing bean definition
        BeanDefinition beanDef = beanFactory.getBeanDefinition("myBean");

        // Modify its metadata
        beanDef.setScope(BeanDefinition.SCOPE_PROTOTYPE);
        beanDef.setLazyInit(true);

        // Add or change property values
        MutablePropertyValues props = beanDef.getPropertyValues();
        props.add("propertyName", "newValue");

        // Dynamically register a new bean
        GenericBeanDefinition newBean = new GenericBeanDefinition();
        newBean.setBeanClass(MyClass.class);
        beanFactory.registerBeanDefinition("dynamicBean", newBean);
    }
}
```

**Difference from** `BeanPostProcessor`

**BeanFactoryPostProcessor**

* Operates on **bean definitions**
* Runs **before any beans are instantiated**
* Modifies container metadata (`BeanDefinition` objects)
* Typical example: `PropertySourcesPlaceholderConfigurer`

**BeanPostProcessor**

* Operates on **bean instances**
* Runs **after bean instantiation**
* Modifies or wraps actual bean objects
* Typical example: `AutowiredAnnotationBeanPostProcessor`

In short:  
🟢 *BeanFactoryPostProcessor works on how beans are defined.*  
🟣 *BeanPostProcessor works on how beans behave once created.*

**Important Notes**

**Execution Order**

* All `BeanFactoryPostProcessor` beans are instantiated **first**, before any application beans.
* Use `@Order` or implement the `Ordered` interface to control the order when multiple processors exist.

**Infrastructure Beans**

* These are **special system-level beans** managed differently than normal beans.
* Avoid depending on other beans — it can create circular initialization issues.

**Static @Bean Methods**

* When declaring one inside a `@Configuration` class, always make it **static** to prevent early creation of the configuration class.

```
@Configuration
public class Config {

    @Bean
    public static BeanFactoryPostProcessor myProcessor() {
        return beanFactory -> {
            // custom modification logic
        };
    }
}
```

**Best Practices**

* Keep logic **simple and efficient** (it runs at container startup).
* Avoid dependencies on other beans.
* Use it for **container-level configuration**, not business logic.
* Prefer built-in implementations when possible.
* Document any dynamic modifications clearly.

**Key Takeaways**

* `BeanFactoryPostProcessor` modifies **bean definitions**, not bean instances.
* It runs **early in the container lifecycle**, before bean creation.
* It’s a **powerful tool** for advanced and dynamic configuration of the Spring container.
* It’s fundamentally different from `BeanPostProcessor`, which works on **fully instantiated beans**.

Question: Which of the following statements regarding @Bean are correct?

### Explanation


**Understanding the** `@Bean` **Annotation Attributes**

The `@Bean` annotation provides several attributes that allow fine-grained control over **bean creation, initialization, and autowiring** in Spring’s Java-based configuration.

**1.** `name` **(Alias:** `value`**) — Bean Names and Aliases ✅**

**Type:** `String[]`  
**Purpose:** Define one or more names for the bean.

You can assign multiple names (aliases) to a single bean.  
The **first name** becomes the **primary bean name**, and the others act as **aliases**.

```
@Bean(name = {"dataSource", "ds", "mainDataSource"})
public DataSource dataSource() {
    return new HikariDataSource();
}
```

All names can be used to reference the same bean.

**2.** `initMethod` **— Initialization Method ✅**

**Type:** `String`  
**Purpose:** Specify the name of the initialization method to call **after dependency injection**.

Only **one** initialization method can be specified.

```
@Bean(initMethod = "initialize")
public MyService myService() {
    return new MyService();
}
```

* The method must have **no arguments**.
* The method is called **after the bean is created** and dependencies are injected.
* Alternative: use `@PostConstruct` on one or more methods within the bean class.

**3.** `destroyMethod` **— Destruction Method**

**Type:** `String`  
**Purpose:** Specify a cleanup method to be called when the container shuts down.

```
@Bean(destroyMethod = "cleanup")
public ConnectionPool connectionPool() {
    return new ConnectionPool();
}
```

* By default, Spring automatically detects `close()` or `shutdown()` methods.
* To disable auto-detection, set `destroyMethod = ""`.

**4.** `autowireCandidate` **— Autowiring Eligibility ✅**

**Type:** `boolean`  
**Default:** `true`  
**Purpose:** Controls whether this bean should be considered as a candidate for autowiring.

```
@Bean(autowireCandidate = false)
public DataSource secondaryDataSource() {
    return new HikariDataSource();
}
```

* Useful when you have **multiple beans of the same type**.
* The bean will be **excluded from automatic autowiring**,  
  but you can still inject it explicitly with `@Qualifier`.

**5. Scope — Not an Attribute of** `@Bean` **❌**

The `@Bean` annotation itself **does not** have a `scope` attribute.  
To define a custom scope, you must use the `@Scope` annotation alongside it.

```
@Bean
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
public MyBean myBean() {
    return new MyBean();
}
```

**Common scopes:**

* `singleton` (default)
* `prototype`
* `request`, `session`, `application`, `websocket` (web-aware)

**Common Usage Patterns**

**Multiple Names**

```
@Bean({"userService", "userManager", "userBusinessLogic"})
public UserService userService() {
    return new UserServiceImpl();
}
```

**With Lifecycle Methods**

```
@Bean(initMethod = "init", destroyMethod = "cleanup")
public CacheManager cacheManager() {
    return new EhCacheCacheManager();
}
```

**With Scope**

```
@Bean
@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
public ShoppingCart shoppingCart() {
    return new ShoppingCart();
}
```

**Exclude from Autowiring**

```
@Bean(name = "backupDataSource", autowireCandidate = false)
public DataSource backupDataSource() {
    return new HikariDataSource();
}
```

**Using** `value` **Alias**

```
@Bean(value = "myBean")     // Same as @Bean(name = "myBean")
@Bean({"bean1", "bean2"})   // Same as @Bean(name = {...})
```

**Common Misconceptions**

* ❌ **Myth:** `@Bean` has a `scope` attribute  
  ✅ **Reality:** Use `@Scope` separately.
* ❌ **Myth:** You can specify multiple init methods in `initMethod`  
  ✅ **Reality:** Only one method name is supported.
* ❌ **Myth:** `autowireCandidate = false` prevents all injection  
  ✅ **Reality:** It only disables *automatic* autowiring; you can still inject via `@Qualifier`.

**Best Practices**

* Use **meaningful bean names** and aliases.
* Use `initMethod` for beans from **external libraries** (when you can’t modify source).
* Use `@PostConstruct` for **custom beans** you control.
* Set `autowireCandidate = false` for **secondary or optional beans**.
* Always combine `@Bean` with `@Scope` when non-singleton scope is needed.

**Key Takeaways**

* `@Bean` supports: multiple names ✅, single init method ✅, and autowire control ✅
* `@Bean` **does not** support `scope` directly ❌ — use `@Scope`
* Lifecycle callbacks: `initMethod`, `destroyMethod`
* Use aliases for flexibility and better configuration clarity

### Explanation


**@EnableAutoConfiguration — Core of Spring Boot’s Opinionated Configuration**

`@EnableAutoConfiguration` is the heart of Spring Boot’s **auto-configuration** system. It embodies Spring Boot’s *“opinionated”* philosophy — configuring your application automatically based on what’s available, while still allowing full customization.

**What Is the "Opinionated Approach"?**

Spring Boot makes **smart, convention-based decisions** about application setup:

* Detects what’s on the **classpath** (e.g., `spring-boot-starter-web`).
* Adapts based on **existing beans** (avoids duplication).
* Reacts to **configuration properties** (e.g., `server.port=9090`).
* Provides **sensible defaults** when nothing is specified.

This approach removes boilerplate, speeds up development, and keeps your configuration clean.

**How** `@EnableAutoConfiguration` **Works**

**1. Classpath Scanning**

Spring Boot inspects all JARs and libraries on the classpath to determine what features should be enabled.

Example:

* If `spring-boot-starter-web` is present → configures MVC, Tomcat, and JSON support.
* If `spring-boot-starter-data-jpa` + a database driver is present → configures JPA and a `DataSource`.

**2. Conditional Configuration**

Auto-configuration classes rely heavily on **conditional annotations**, such as:

* `@ConditionalOnClass` — activates only if a specific class is on the classpath.
* `@ConditionalOnMissingBean` — activates only if no user-defined bean of that type exists.
* `@ConditionalOnProperty` — activates only if a property is defined.

These conditions ensure that **auto-configuration is applied only when appropriate**, and backs off when custom configurations exist.

**3. Intelligent Defaults**

If you haven’t defined a bean or property, Spring Boot supplies defaults:

* Default web server port: **8080**
* Default in-memory database: **H2**
* Default security: basic login form with generated password

Defaults can be **overridden easily** by:

* Adding your own bean definitions.
* Setting properties in `application.properties` or `application.yml`.

**Examples of Auto-Configuration in Action**

**Web Application**

* Classpath: `spring-boot-starter-web`
* Auto-configures: Embedded Tomcat, `DispatcherServlet`, JSON via Jackson
* Default port: `8080` (override with `server.port=9090`)

**Database**

* Classpath: `spring-boot-starter-data-jpa` + JDBC driver
* Auto-configures: `DataSource`, `EntityManagerFactory`, `TransactionManager`
* Default: in-memory H2 database if no external one provided

**Security**

* Classpath: `spring-boot-starter-security`
* Auto-configures: `UserDetailsService`, login form, password encoder
* Default: all endpoints secured

**Usage Patterns**

**Direct Use (Uncommon)**

```
@Configuration
@EnableAutoConfiguration
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}
```

**Via** `@SpringBootApplication` **(Recommended)**

```
@SpringBootApplication // includes @EnableAutoConfiguration
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}
```

`@SpringBootApplication` combines:

* `@Configuration`
* `@EnableAutoConfiguration`
* `@ComponentScan`

**Excluding Auto-Configuration**

You can exclude specific auto-configurations if not needed:

**Annotation-based:**

```
@SpringBootApplication(exclude = { DataSourceAutoConfiguration.class })
```

**Property-based:**

```
spring.autoconfigure.exclude=org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
```

**Customizing Auto-Configuration**

**Override defaults by defining your own beans:**

```

    return new HikariDataSource(); // replaces auto-configured DataSource
}
```

**Or customize using properties:**

```
spring.datasource.url=jdbc:mysql://localhost/mydb
spring.datasource.username=user
spring.datasource.password=pass
```

**How Spring Boot Decides What to Configure**

1. Scans classpath for known libraries.
2. Checks if user-defined beans already exist.
3. Reads configuration properties.
4. Applies auto-configurations **conditionally**.
5. **Backs off** when manual configuration is detected.

**Benefits of the Opinionated Approach**

* **Zero Configuration Needed:**  
  Works immediately with sensible defaults.
* **Rapid Development:**  
  Get a working app in minutes — no XML.
* **Production-Ready Defaults:**  
  Logging, security, and metrics are enabled out of the box.
* **Full Control:**  
  You can exclude, override, or customize any configuration.

**Why Other Options Are Wrong**

* `@EnableSpringBootConfig` ❌ — doesn’t exist.
* `@OpinionatedConfig` ❌ — describes philosophy, not an annotation.
* `@AutoConfig` ❌ — invalid (missing “Enable” prefix).
* ✅ **Correct:** `@EnableAutoConfiguration`

**Related Annotations**

* `@SpringBootApplication` — Meta-annotation that includes `@EnableAutoConfiguration`.
* `@SpringBootConfiguration` — Specialization of `@Configuration` for Boot apps.
* `@AutoConfiguration` — Used *internally* by Spring Boot to define auto-configuration classes.

**Common Misconceptions**

* ❌ *“Auto-configuration is magic and inflexible”*  
  ✅ It’s fully transparent and can be overridden anytime.
* ❌ *“You can’t control what gets configured”*  
  ✅ You can exclude or replace any configuration.
* ❌ *“It only works with Spring Boot starters”*  
  ✅ It works with **any classpath library**.

**Best Practices**

* Use `@SpringBootApplication` on your main class.
* Enable debug mode (`--debug`) to see applied/excluded configurations.
* Exclude unnecessary configurations for faster startup.
* Prefer **property overrides** before custom bean definitions.
* Review the **Auto-Configuration Report** in your IDE or Actuator.

**Key Takeaways**

* `@EnableAutoConfiguration` powers Spring Boot’s **automatic, opinionated setup**.
* It’s included by default via `@SpringBootApplication`.
* It configures your app based on classpath and conditional rules.
* It’s **flexible**, **transparent**, and **customizable** — the foundation of “**convention over configuration**” in Spring Boot.

Question: Which of the following statements are incorrect regarding Spring field injection with @Autowired?

**(A)** Spring needs setter methods to inject value in a field annotated with @Autowired

**(B)** Injected field can have any access modifier, including private

**(C)** @Autowired uses the field name as a default qualifier

**(D)** @Autowired can't be used on fields to achieve field injection
### Explanation


In Spring, the `@Autowired` annotation facilitates dependency injection, allowing the framework to inject bean dependencies into a class. Field injection is one method of achieving this, where dependencies are injected directly into fields.​

**Key Points:**

* **Field Injection:** By annotating a field with `@Autowired`, Spring injects the required dependency directly into that field. For example:​
```java

  KopiujEdytuj@Component
  public class MyService {
      @Autowired
      private MyRepository myRepository;
  }
  ```

In this example, Spring injects an instance of `MyRepository` into the `myRepository` field of `MyService`.​

* **Access Modifiers:** Fields annotated with `@Autowired` can have any access modifier, including private. Spring uses reflection to perform the injection, so the access level does not hinder the process.​
* **Setter Methods:** Field injection does not require setter methods. Spring sets the field's value directly, making setter methods unnecessary for this purpose.​
* **Default Behavior:** `@Autowired` performs injection by type. If multiple beans of the same type exist, ambiguity arises, and Spring may throw an exception. To resolve this, the `@Qualifier` annotation can specify which bean to inject.​

**Considerations:**

While field injection is convenient, it has notable drawbacks:​[stackoverflow.com+1baeldung.com+1](https://stackoverflow.com/questions/39890849/what-exactly-is-field-injection-and-how-to-avoid-it)

* **Testability:** Field injection can complicate unit testing. Without a proper constructor or setter, injecting mock dependencies becomes challenging, often requiring reflection or frameworks like Mockito.​
* **Immutability:** Field injection prevents the use of `final` modifiers on injected fields, hindering the creation of immutable classes.​
* **Design Clarity:** Dependencies injected via fields are not immediately visible in the class's public API, potentially obscuring the class's dependencies and violating the principle of explicit dependencies.​

**Best Practices:**

Due to these drawbacks, constructor injection is generally recommended over field injection:​

* **Constructor Injection:** Allows for immutable dependencies and makes the class's requirements explicit.​
```java

  KopiujEdytuj@Component
  public class MyService {
      private final MyRepository myRepository;

      @Autowired
      public MyService(MyRepository myRepository) {
          this.myRepository = myRepository;
      }
  }
  ```

In this example, `MyRepository` is a mandatory dependency for `MyService`, enforced through the constructor.​


4. NONE

Loads a regular ApplicationContext without any web features. Use this for testing non-web components like services, repositories, or batch jobs where web infrastructure is unnecessary.

Example:

```
@SpringBootTest(webEnvironment = WebEnvironment.NONE)
public class ServiceTest {
    @Autowired
    private UserService userService;
}
```

Best Practices:

* Use MOCK for controller tests with MockMvc (fastest execution)
* Use RANDOM\_PORT for integration tests requiring real HTTP (avoids port conflicts)
* Use NONE for testing non-web components (lightest weight)
* Avoid DEFINED\_PORT in CI/CD environments to prevent port conflicts

Performance Considerations:

NONE < MOCK < RANDOM\_PORT/DEFINED\_PORT

Tests run faster with simpler web environments. Choose the lightest option that meets your testing requirements.

Common Use Cases:

• Unit testing controllers → MOCK + MockMvc

• Integration testing REST APIs → RANDOM\_PORT + TestRestTemplate

• Testing services/repositories → NONE

• Testing with external tools → DEFINED\_PORT (specific port required)

Choosing the right webEnvironment significantly impacts test execution speed, reliability, and maintainability of your test suite.
